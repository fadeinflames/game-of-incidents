# Threat model v1

Статус: v1. Заменяет v0, написанную для внутренней команды на машине разработчика. Описывает развёртывание с открытой регистрацией. Статусы контролей сверены с кодом после первой волны исправлений по аудиту. То, что требует работ на сервере, помечено «не сделано» и описано в `docs/runbook-prod-install.md`.

Правило: остаточный риск считается принятым только после письменного решения сопровождающего с датой. Прежние решения 2026‑09‑29 и 2026‑09‑30 принимались для внутренней аудитории и на публичную не переносятся. Где нового решения нет, в таблице рисков стоит «открыто».

## Активы

| Актив | Почему важен |
|---|---|
| Хост: выделенный сервер, ядро, rootless‑демон Docker пользователя `wom`, его сокет | компрометация = всё остальное |
| БД платформы: хеши паролей (bcrypt), cookie‑сессии, результаты, адрес клиента у сессии (`TrainingSession.clientIp`), **секретные скрипты сценариев** (`check.sh`, `solve.sh`), архивы заявок авторов | утечка эталонов обесценивает сценарии; учётные данные и адреса — персональные данные |
| Песочницы других пользователей | приватность и честность результатов |
| Внутренняя сеть compose (web, orchestrator, db) | доступ к БД и внутреннему API оркестратора |
| Секреты платформы: `INTERNAL_TOKEN`, пароль БД, TLS‑ключи Caddy | |
| Ресурсы и адрес сервера: CPU, память, диск, исходящий трафик с IP прода | исчерпание = отказ для всех; исходящий трафик со стенда = жалобы на адрес прода |
| Бэкапы БД на сервере и их копия на другой машине | в дампе всё содержимое БД, дамп не зашифрован |

## Границы доверия

```
Интернет ──TLS──► Caddy ──► web (Next.js) ──HTTP + X-Internal-Token──► orchestrator ──unix socket──► rootless dockerd (uid wom)
                    │                                                        │
                    └──WSS /ws/term/<id> (одноразовый токен)─────────────────┘
                                                                             ▼
                              Linux‑сессия: один контейнер, сеть internal на сессию, без egress
                              Kubernetes‑сессия: кластер kind (ноды privileged) + tools‑контейнер (терминал) + runner (скрипты),
                                                 bridge wk8s<id>, исходящие соединения режет egress‑guard
```

Доверяем: Caddy, web, orchestrator, демону Docker, БД, администратору. Не доверяем: браузеру, всему, что выполняется внутри песочницы и внутри кластера сессии, содержимому заявок авторов (до решения модератора и после него: модератор видит файлы, но не обязан найти всё).

## Атакующие

- **A3. Любой зарегистрированный пользователь — основной атакующий.** Регистрация открыта: логин и пароль, без почты. Получает root (через `sudo`) в своей песочнице или cluster‑admin в своём кластере. Цели: выйти из песочницы, добраться до платформы или чужих сессий, занять ресурсы, использовать стенд для исходящего трафика, обмануть грейдер.
- **A4. Автор заявки.** Тот же зарегистрированный пользователь, загружающий zip со сценарием: Dockerfile, манифесты, скрипты. Его код выполняется на сервере после действия модератора (сборка образа, регресс) и после публикации.
- **A5. Анонимный посетитель.** Перебор паролей, массовая регистрация, нагрузка на публичные эндпоинты.
- **A2. Ошибка пользователя.** `rm -rf /`, fork‑bomb, заполнение диска: без умысла, с теми же последствиями для хоста.
- **A1. Администратор и модератор.** Доверенные. Роль одна (`admin`): отдельной роли модератора нет.

## Угрозы и контроли

Статус: **закрыто** — контроль есть в коде и проверен; **частично** — есть, но с перечисленным остатком; **открыто** — контроля нет.

| ID | Угроза | Контроль и где он | Статус |
|---|---|---|---|
| T‑1 | Побег из контейнера в хост через уязвимость ядра или лишние capabilities | Rootless Docker: root песочницы на хосте — непривилегированный uid. Seccomp по умолчанию, `cap-drop ALL` и короткий allow‑list; имя capability нормализуется (`CAP_`, регистр, пробелы) и сверяется с запретным списком в `packages/runtime/src/docker.ts`, есть unit‑тесты. `privileged`, host network и монтирования хоста запрещены кодом. `no-new-privileges` включается только для песочниц без `sudo`; у всех 22 сценариев каталога `sudo` включён, значит флаг выключен (решение ADR‑0001). Обновления ядра: `unattended-upgrades` только для пакетов Debian, перезагрузка вручную | частично, остаток — **R‑1** |
| T‑2 | Доступ из песочницы к сокету Docker или к сети платформы | Сокет монтируется только в оркестратор. Linux‑сессия: отдельная сеть `internal` на сессию. | T‑3 | Песочница A видит песочницу B | Сеть на сессию, общих томов нет, свой pid‑namespace. Kubernetes: свой кластер, kubeconfig только своего API‑сервера. Автоматического теста изоляции между кластерами нет | частично (нет теста) |

## Ждут решения (помимо таблицы рисков)

- **Ёмкость.** Лимит ноды kind ограничивает одну сессию, а не сумму: выбрать `KIND_NODE_MEMORY_MB` и `MAX_K8S_SESSIONS` так, чтобы худший случай помещался в 62 ГБ, либо принять переподписку.
- **Блокировка входа по логину.** 10 неверных попыток за 15 минут закрывают вход под известным логином, включая администратора.
- **Срок хранения `clientIp`.** Адрес клиента у сессии хранится бессрочно.
- **Очередь при мёртвом egress‑guard.** Отказ проверяется при создании сессии; сессии, уже стоящие в очереди, будут подняты.
- **IPv6.** Лимиты по адресу не объединяют адреса одной /64. Сейчас у домена нет AAAA‑записи.
- **Шифрование дампов.** Потеря ключа равна потере всех копий.
- **Ключ внешней машины для копии бэкапов (T‑18).** Ограничить его командой `rrsync -ro`: см. `docs/runbook-prod-install.md`, §6.

## Что не рассматривается

DDoS на Caddy, компрометация провайдера сервера, фишинг администратора, физический доступ.

Порядок действий при подозрении на побег из песочницы или злоупотребление стендом: `docs/runbook-prod-install.md`, раздел «Инцидент в песочнице».

## Как устроена egress‑изоляция Kubernetes‑сессий

Kind не стартует на docker‑сети `internal` (ноде нужен шлюз), поэтому сети кластерных сессий — обычные bridge'и с предсказуемым именем интерфейса `wk8s<id>`. Сервис `egress-guard` (`images/egress-guard`, `network_mode: host` и `privileged`, то есть внутри сетевого namespace rootless‑демона) держит в `FORWARD` цепочку `WOM-EGRESS`: `ESTABLISHED,RELATED → ACCEPT`, затем `-i wk8s+ ! -o wk8s+ → DROP`. Под, нода kind и tools‑контейнер не могут открыть соединение за пределы своего bridge'а: ни в интернет, ни в LAN, ни к сервисам хоста. Соединения, открытые снаружи (оркестратор → API‑сервер, runner‑контейнеры), и ответы на них проходят. Изоляцию bridge'ей друг от друга дают штатные цепочки Docker.

Раз в 30 секунд guard заново проверяет правила и после успешного прохода пишет время в `/run/wom-egress/heartbeat` (том, который оркестратор читает только на чтение). Heartbeat старше 150 секунд (`EGRESS_HEARTBEAT_MAX_AGE_SEC`) или его отсутствие означает `stale`: новые Kubernetes‑сессии получают отказ с понятным текстом, Linux‑сессии продолжают работать. При остановке guard правила остаются в namespace, удаляется только heartbeat.

Проверка вручную: из tools‑контейнера живой сессии `wget -T 3 http://1.1.1.1` заканчивается таймаутом; `docker inspect -f '{{.State.Health.Status}}' wom_egress_guard` отвечает `healthy`.

- **Снимок сценария в сессии (2026-10-04).** `TrainingSession.scenarioSnapshot` содержит скрипт проверки; он очищается вместе с `runtimeHandle` при завершении сессии. Сессия, убитая до выдачи стенда, хранит снимок до суточной очистки.
