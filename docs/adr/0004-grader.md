# ADR‑0004. Механизм проверки (grader)

- Статус: **принято** (2026‑09‑29, B + D; R‑4 закрыт read‑only rootfs вместо принятия)
- Дата: 2026‑09‑29
- Роли: техлид, backend, автор сценариев, security

## Контекст

По нажатию «Проверить» платформа должна выполнить проверку внутри окружения и вернуть структурированный результат: пройдено/не пройдено по каждому критерию + сообщение, не раскрывая решение. Пользователь — root в песочнице и может читать любой файл внутри неё и видеть процессы. Грейдер должен проверять результат, а не способ (правило «честной поломки»). Тот же механизм нужен регресс‑тесту сценариев (ADR‑0005: свежая песочница → `false`; после `solve` → `true`).

## Варианты

| Вариант | Как защищён от чтения | Что видит пользователь | Сложность |
|---|---|---|---|
| A. `check.sh` лежит в образе, оркестратор делает `docker exec check.sh` | никак — файл читается | всё | минимальная |
| B. **`check.sh` хранится в БД платформы и подаётся в песочницу через stdin**: `docker exec -i <ctr> /bin/sh -s` со скриптом в stdin; на диск песочницы не пишется | скрипт не появляется в файловой системе и в `argv`; во время выполнения теоретически виден через `/proc/<pid>/fd/0` (пайп) и в `ps` как `sh -s` | процесс `sh -s` в течение секунд проверки | малая; тот же путь, что exec терминала |
| C. Постоянный агент внутри песочницы с REST API (как в SadServers) | агент — root‑процесс, пользователь может его убить или подменить | агент и его бинарник | средняя; плюс сборка агента в каждый образ |
| D. Проверки только снаружи (оркестратор ходит по сети в контейнер: HTTP, TCP, `docker exec` отдельных команд) | полностью вне песочницы | ничего | зависит от сценария; не все критерии выражаются снаружи |

## Решение

**B как основной механизм + D как дополнение.** В `environment` сценария:

- `check: check.sh` — выполняется по B, stdout — JSON:

  ```json
  {"passed": false, "criteria": [
    {"id": "nginx-running", "ok": true,  "message": "nginx отвечает на :80"},
    {"id": "upstream-200",  "ok": false, "message": "GET / вернул 502"}
  ]}
  ```

  Код возврата ≠ 0 или невалидный JSON → результат `error`, показывается «проверка не удалась, попробуй ещё раз», в лог — stderr.
- `probes` (опционально, D) — список внешних проверок, которые выполняет оркестратор без входа в песочницу: `{kind: http, url: "http://{sandbox}:80/", expectStatus: 200}`, `{kind: tcp, port: 5432}`. Результаты объединяются с критериями `check.sh`.
- `solve: solve.sh` — тем же способом B, только из регресс‑теста и админского «показать эталон»; в пользовательской сессии никогда не выполняется.

Ограничения выполнения грейдера: `timeout 60 s`, `User: root`, тот же контейнер (нет отдельного «чистого» контейнера, потому что проверяется состояние именно этого окружения).

Что скрывается от пользователя: текст `check.sh`, `solve.sh`, сообщения критериев уровня `hint` (в `check.sh` можно пометить критерий `"reveal": "after_finish"`, тогда сообщение показывается только в разборе).

Принимаемые риски (в threat model):

- R‑4: пользователь может подменить утилиты, которыми пользуется грейдер (`curl`, `psql`, `ss`). **Риск решено не принимать**, а закрыть жёстким контролем: корневая ФС песочницы только для чтения (ADR‑0001), бинарники в `/bin`, `/sbin`, `/usr` неизменяемы, установка пакетов невозможна. `check.sh` дополнительно вызывает утилиты по абсолютным путям и запускается с чистым `PATH=/usr/sbin:/usr/bin:/sbin:/bin` и без переменных окружения пользователя (`env -i`), чтобы исключить подмену через `PATH`, `LD_PRELOAD` и алиасы. Остаточный риск после этого — подмена через записываемые пути сценария (`/etc/ld.so.preload` в `/etc`): грейдер запускается с `LD_PRELOAD` пустым, а линтер запрещает объявлять `/etc/ld.so.preload` записываемым отдельно от `/etc`; `/etc/ld.so.preload` должен дополнительно перекрываться read‑only монтированием пустого файла при создании контейнера. До 2026‑10‑01 это было записано, но не реализовано; реализовано в коде первой волны исправлений по аудиту, подробности и отличия от этого текста — в разделе «Реализация и отклонения».
- R‑5: во время проверки (секунды) пользователь может подсмотреть скрипт через `/proc`. Для внутренней аудитории риск принимается; при открытии наружу — переход на D‑only или на C с проверкой целостности.

## Последствия

- Плюс: никакой новой инфраструктуры, тот же `exec`‑путь, что и терминал.
- Плюс: регресс‑тест сценария — три вызова того же `GraderRunner`.
- Минус: проверка длится секунды, статус `checking` виден в UI.
- Минус: авторы обязаны писать `check.sh` на POSIX `sh` (без bash‑измов), потому что базовый образ сценария может быть минимальным. Линтер проверяет shebang.

## Принятое решение

2026‑09‑29: B + D приняты. R‑5 принят. R‑4 не принят — закрыт техническими мерами выше.

## Реализация и отклонения (дополнение 2026‑10‑01)

Раздел сверен с кодом после первой волны исправлений по аудиту. Решение выше не менялось, ниже — что реализовано иначе или добавлено.

- **Окружение скриптов платформы.** `break/check/solve` выполняются через `DockerRuntimeProvider.runScript` с явным списком `Env`, а не `env -i`: `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`, `LD_PRELOAD=` (пусто), `HOME=/nonexistent`, `CURL_HOME=/nonexistent`, `PSQLRC=/nonexistent/.psqlrc`. Домашний каталог не `/root`, потому что `/root` записываем игроком, а значит в нём можно положить `~/.psqlrc` и `~/.curlrc`, которые подменяют вывод `psql` и `curl` внутри грейдера. `PSQLRC` указывает на путь, который игрок создать не может, а не на `/dev/null`: `psql` сначала пробует файл `<PSQLRC>-<версия>`, а `/dev` в песочнице — записываемый tmpfs.
- **Монтирования платформы.** Вместо «пустого bind‑mount'а» поверх `/etc/ld.so.preload` песочница получает два платформенных монтирования `/dev/null` только для чтения (`HostConfig.Mounts`, константа `PLATFORM_MOUNTS`): `/etc/ld.so.preload` и `/nonexistent/.curlrc` (без второго `curl` берёт домашний каталог из `passwd` и читает `/root/.curlrc`). Источник — всегда `/dev/null`, значения сценария в источник не попадают, `Binds` остаётся пустым, так что запрет монтирований данных хоста (ADR‑0001) не нарушен. Побочный эффект: в каждой песочнице на неизменяемой корневой ФС есть каталог `/nonexistent` с одним файлом. Запуск песочниц с этими монтированиями на живом rootless‑демоне проверяет интегратор при выкладке.
- **Таймаут.** Грейдер и `break` ограничены `GRADER_TIMEOUT_MS` и `BREAK_TIMEOUT_MS` (по умолчанию 240 с, на проде `BREAK_TIMEOUT_MS=300000`), а не 60 с: кластерные грейдеры ждут раскатки через `kubectl exec`. Срок дополнительно исполняется внутри песочницы через `timeout -s KILL`, если он есть в образе. Правило для авторов: `break.sh` должен укладываться в 240 с.
- **Остаток по R‑4.** `/etc/ld.so.cache` и `/etc/ld.so.conf.d` записываемы, игрок с `sudo` может через `ldconfig` подставить библиотеку процессам грейдера. Перекрыть кэш монтированием нельзя: поиск библиотек в образах сломается. Системный `psqlrc` (в Debian — `/etc/postgresql-common/psqlrc`) `psql` читает независимо от `PSQLRC`, поэтому грейдеры обязаны звать `psql -X`, а `curl` — с `-q` первым аргументом; линтер предупреждает об этом (`grader-psql-rc`, `grader-curl-rc`). Статус остатка — в `docs/threat-model.md` (R‑4).
- **Не реализовано из решения.** Раздел `probes` (внешние HTTP/TCP‑проверки оркестратора) и критерии с `"reveal": "after_finish"` отсутствуют в схеме формата v2 (`packages/scenario/src/schema.ts`) и в коде оркестратора; грейдер работает только по варианту B. Сообщения критериев показываются игроку сразу. Если `probes` понадобятся, их безопасность (T‑10 в threat model) надо разбирать заново.
- **Проверки в регрессе.** `wom scenario test` гоняет свежее окружение (ожидается «не решено», если `test.baseline` не `skip`), `solve.sh` (ожидается «решено») и пробы харднинга. Юнит‑тесты состава `HostConfig` и окружения `runScript` — `packages/runtime/test/docker.test.ts`.
