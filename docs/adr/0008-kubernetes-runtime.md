# ADR‑0008. Kubernetes‑runtime для кластерных сценариев (kind)

- Статус: **принято** (2026‑09‑30, вариант A; тёплый пул отклонён: ожидание до минуты приемлемо)
- Дата: 2026‑09‑30
- Роли: техлид, platform, security, автор сценариев

## Контекст

Из 18 сценариев `wom-games` четыре воспроизводимы только в Kubernetes, ещё пять теряют суть при переносе на один хост. Кейс «Фантомная сеть» тоже кластерный: Envoy, поды order-service и payment-proxy, liveness‑пробы, PgBouncer. Для таких кейсов рассматривается kind.

ADR‑0001 выбрал Docker‑контейнеры с харднингом за интерфейсом `RuntimeProvider`. Kubernetes‑сценарии — вторая реализация этого интерфейса, а не замена первой.

Вывод: на этой машине помещается 8–10 одновременных single‑node кластеров по памяти; по CPU разумный предел — 4–5 активных сессий с нагрузочными сценариями.

## Решение (предлагается)

**A: кластер kind на сессию, с тёплым пулом.** Причины: сценарии «Фантомной сети» и из `wom-games` включают перезапуски подов, liveness‑kill, drain, DiskPressure — на общем кластере это либо невозможно, либо бьёт по соседям; изоляция «свой кластер» проще объяснить и проверить, чем RBAC; памяти на машине разработчика хватает; 40 с холодного старта закрывается тёплым пулом.

Как встраивается:

- `KubernetesRuntimeProvider` (вторая реализация `RuntimeProvider`): `create` = взять кластер из пула или `kind create cluster --config` с именем `wom-k8s-<sessionId>` и метками на контейнерах нод; `runScript` = выполнить `break/check/solve` в **служебном контейнере оркестратора** с `kubectl` и admin‑kubeconfig кластера (скрипты не попадают ни в кластер, ни в песочку пользователя); `destroy` = `kind delete cluster`; `list` = kind‑ноды по меткам.
- **Терминал пользователя** — не нода kind, а обычная харднутая песочка из ADR‑0001 (образ `wom-tools`: kubectl, k9s, helm, jq, curl) с kubeconfig, смонтированным в `/home/oncall/.kube/config`, подключённая к docker‑сети кластера kind. Пользователь видит кластер как SRE видит прод: через API, а не через shell ноды. `sudo` в песочке остаётся, но на ноду не влияет.
- Формат v2: `environment.kind: kubernetes`, `cluster: { nodes: 1 | 3, image: kindest/node:v1.37.0 }`, `manifests: ./k8s/` (применяются при подготовке), `images: [...]` (предзагружаются в ноду через `kind load`), `tools: wom-tools:dev`. `break.sh`/`check.sh`/`solve.sh` — те же POSIX‑скрипты, но с `kubectl` в PATH и `KUBECONFIG` (грейдер проверяет результат через API: статусы подов, ответы сервисов через port‑forward/exec, `pg_stat_activity` через `kubectl exec`).
- Пул: параметр `K8S_WARM_POOL=1` (dev) / `2` (прод); reconciler держит столько пустых кластеров с меткой `wom.pool=k8s` и удаляет лишние.
- Квоты: отдельный лимит `MAX_K8S_SESSIONS` (dev: 3), потому что сессия с кластером весит в 10 раз больше контейнерной.

## Security (дополнение к threat model)

- **T‑15 / R‑6.** Нода kind — privileged‑контейнер: внутри него всё разрешено (mount, модули не грузятся, но capabilities полные в пределах user namespace). Побег из пода → в ноду → далее ограничен user namespace rootless‑демона: root ноды = пользователь rootless‑демона на хосте без capabilities вне userns. Для внутренней команды предлагается **принять как R‑6** с тем же обоснованием, что R‑1; при открытии наружу — kind только в отдельной VM.
- Пользователь получает cluster‑admin **своего** кластера; чужих кластеров он не видит: kubeconfig указывает на apiserver конкретного кластера, сети kind изолированы друг от друга docker‑сетями (проверить позже: `internal`‑сеть для нод и запрет на egress по умолчанию — у kind‑нод egress нужен для `kind load`? нет, образы грузятся через Docker API; но CoreDNS/pull наружу должны быть закрыты — это отдельная проверка).
- Docker socket по‑прежнему только у оркестратора; kind вызывается им.

## Последствия

- Плюс: сценарии `wom-games` про Kubernetes и «Фантомная сеть» воспроизводятся один в один, включая ловушки (расширить пул PgBouncer, убрать liveness, откатить релиз).
- Плюс: интерфейс `RuntimeProvider` подтверждает свою ценность — платформа не переписывается.
- Минус: 40 с холодный старт, ≈ 550 МБ на сессию, ≈ 1 ядро под нагрузкой; на машине разработчика — 3–4 параллельные кластерные сессии.
- Минус: образы приложений сценария (Java/Go/Python, PgBouncer, PostgreSQL, Envoy) надо собирать и грузить в ноду (`kind load`), это +10–30 с на старт без пула.
- Минус: ещё один провайдер = ещё один набор тестов (интеграционные против настоящего kind на машине разработчика).

## План (если принято)

1. `KubernetesRuntimeProvider` + образ `wom-tools` + пул + один тривиальный сценарий «Сломанные пробы» (readiness на устаревший путь) как walking skeleton.
2. «Фантомная сеть» как живой кластерный сценарий: манифесты order-service / payment-proxy / PgBouncer / PostgreSQL / заглушки эквайеров / edge; поломка «эквайер А молчит» + генератор нагрузки с ретраями; грейдер по результату (заказы отвечают ≤ 3 с, нет `idle in transaction`, нет висящих соединений); подсказки по таймингу из шпаргалки GM; разбор с ловушками.
3. Дальше — остальные кластерные сценарии (перенесены).

## Принятое решение

2026‑09‑30: вариант A принят, тёплый пул не реализуется (ожидание до минуты приемлемо), целевое время старта кластерной сессии ≤ 60 с. Риск R‑6 принят вместе с ADR (внутренняя команда, машина разработчика).

## Реализация (первый этап, 2026‑09‑30)

- `packages/runtime`: `KubernetesRuntimeProvider` поверх `DockerRuntimeProvider`; `RuntimeRegistry` выбирает провайдер по `spec.kubernetes` / `handle.provider`. Оркестратор и CLI используют реестр.
- Сессия = docker‑сеть `wom-k8s-<sessionId>` → `kind create cluster` на ней (`KIND_EXPERIMENTAL_DOCKER_NETWORK`) → `kind get kubeconfig --internal` → `kind load` образов из `images` → tools‑контейнер (`wom-tools:dev`, ADR‑0001 харднинг, `sudo` только внутри него) с kubeconfig в `~/.kube/config` пользователя `oncall` → манифесты применяет **runner** (эфемерный контейнер того же образа без sudo) → `break.sh`. `check.sh`/`solve.sh` тоже выполняются в runner'е: пользовательский tools‑контейнер и нода их не видят.
- **Отклонение от ADR‑0001 (R‑7):** сеть кластерной сессии **не** `internal`. Entrypoint ноды kind программирует iptables по адресу шлюза сети, а у internal‑сетей Docker шлюза нет (`iptables-restore: host/network '' not found`, проверено с `--retain`). Поэтому у нод и tools‑контейнера кластерной сессии есть egress. Закрывается позже (правила на хосте или egress‑прокси); для внутренней команды принимается вместе с R‑6.
- Замеры на машине разработчика: создание сессии (кластер + образ + манифесты) 37,6 с; полный регресс `wom scenario test scenarios/broken-probes` 59 с; после уборки 0 кластеров, 0 контейнеров, 0 сетей.
- Формат v2: `environment.kind: kubernetes`, `cluster.nodes`, `manifests: ./k8s` (инлайнится в БД загрузчиком), `images: [...]`, `image` = tools‑образ; `test.baseline: pass|fail|skip` — что грейдер должен сказать на **неломаном** окружении (для «Сломанных проб» — `fail`, потому что грейдер требует релиз, которого до поломки нет).
- Квота `MAX_K8S_SESSIONS` (dev: 3), колонка `TrainingSession.provider`. Таймаут provisioning поднят до 300 с.
- Оркестратор‑образ содержит `kind` v0.33.0 и docker‑cli; `kind` ходит в rootless‑демон через смонтированный сокет.

## Дополнения по ходу второго этапа (2026‑09‑30)

- **Загрузка образов в ноду.** Rootless‑демон Docker 29 использует containerd image store; `kind load docker-image` для мультиплатформенных образов (`postgres:16-alpine`, `nginx:1.27-alpine`) падает с `ctr: content digest … not found`, потому что архив ссылается на слои чужих платформ. Провайдер сохраняет образ явно для `linux/amd64` (`docker save --platform`) и грузит `kind load image-archive`; публичные образы докачиваются демоном перед этим.
- **Reconciler и кластеры CLI.** Кластеры `wom-k8s-test-*` / `wom-k8s-run-*` (созданные `wom scenario test|run`) помечаются владельцем `cli` с временем создания ноды и не удаляются два часа — иначе оркестратор убивал тестовые кластеры через 30 с (нода с кодом 137).
- **Отладка.** `WOM_KIND_RETAIN=1` оставляет кластер и сеть при ошибке создания (`docker logs <cluster>-control-plane`).
- **Таймауты.** Грейдеры и поломки кластерных сценариев ходят через `kubectl exec` и ждут rollout'ов: `GRADER_TIMEOUT_MS` и `BREAK_TIMEOUT_MS` по умолчанию 240 с, в CLI‑регрессе 240 с для kubernetes.
- **«Фантомная сеть»** (`scenarios/phantom-network`): 7 Deployment'ов (postgres, acquirer‑a/b, payment‑proxy, order‑service ×3, edge‑gateway nginx, load‑generator с ретраями), 3 образа. Регресс: создание 55 с, каскад после поломки виден через 22 с, всего 2 мин 51 с. Грейдер по результату: заказы ≤ 5 с, нет `idle in transaction` старше 10 с, нет вызовов к эквайеру А, застрявших дольше 10 с (у живых подов), order‑service стабилен, liveness на месте.

## Дополнение 2026‑10‑01: публичный прод, лимиты нод, пересмотр R‑6

Что изменилось после первой волны исправлений по аудиту и что остаётся открытым.

**Исправление устаревших мест выше.** Тёплого пула нет (отклонён), параметр `K8S_WARM_POOL` не реализован. R‑7 (egress кластерных сессий) закрыт 2026‑09‑30: сеть сессии — bridge `wk8s<id>`, исходящие соединения режет сервис `egress-guard`; с 2026‑10‑01 он fail‑closed (heartbeat, отказ оркестратора в кластерных сессиях при устаревшем heartbeat, правила остаются при остановке guard); описание — `docs/threat-model.md`, раздел «Как устроена egress‑изоляция». Остаток по обходу guard (DNS, `INPUT` к шлюзу, IPv6, позиция правила в `FORWARD`) — R‑9 в threat model. Квота `MAX_K8S_SESSIONS`: dev 3, прод 6; одновременно поднимается `MAX_K8S_PROVISIONING` кластеров (dev 1, прод 2), остальные сессии ждут в очереди.

**Лимиты нод (новое).** До этой волны лимиты CPU, памяти и числа процессов были только у tools‑контейнера и runner'а, а ноды kind работали без лимитов: игрок — cluster‑admin, и одна сессия могла занять весь сервер. Теперь после успешного `kind create cluster` ко всем контейнерам с меткой `io.x-k8s.kind.cluster=<имя>` применяется `container.update` с лимитами: память `KIND_NODE_MEMORY_MB` (по умолчанию 4096, запас большой, потому что OOM‑kill ноды убивает весь кластер), CPU `KIND_NODE_CPUS` (2), процессы `KIND_NODE_PIDS` (8192); пустое, нечисловое или неположительное значение даёт значение по умолчанию. Ошибка применения лимита пишется в stderr оркестратора (`kind node limits not applied`) и сессию не роняет. Остаётся открытым:
- лимит ограничивает одну ноду, а не сумму: 6 кластерных сессий × до 4 нод × 4 ГБ — это 96 ГБ при 62 ГБ на сервере; выбор значений `KIND_NODE_MEMORY_MB` и `MAX_K8S_SESSIONS` либо принятие переподписки — **открыто**;
- не сделаны `kubeadmConfigPatches` с `systemReserved` и `evictionHard`, `LimitRange` и `ResourceQuota` по умолчанию и проба в регрессе на то, что игрок не снимает лимит из привилегированного пода;
- в rootless‑демоне лимиты действуют, только если пользователю делегированы cgroup v2 контроллеры `memory`, `pids` и `cpu` (команда проверки — в runbook).

**Проверка образа ноды и capabilities.** `cluster.nodeImage` принимается только вида `kindest/node:vX.Y.Z` с необязательным `@sha256:<64 hex>` и пишется в конфиг kind как строка JSON (раньше значение с переводом строки позволяло дописать в YAML‑конфиг чужие поля). Проверка стоит и в схеме формата v2, и в `KubernetesRuntimeProvider.create()` независимо. Если в БД есть сценарий с другим `nodeImage`, его сессии перестанут создаваться с ошибкой «cluster.nodeImage must look like…» (в репозитории таких нет).

**R‑6 для публичной аудитории.** Решение 2026‑09‑30 «принять R‑6» относилось к внутренней команде на машине разработчика и при регистрации для любого пользователя не действует. Условие этого ADR «при открытии наружу — kind только в отдельной VM» не выполнено: ноды (`--privileged`, без seccomp, PodSecurity не включён) работают в том же rootless‑демоне, что БД и секреты платформы, под тем же пользователем `wom`, у которого на проде есть `NOPASSWD` sudo (T‑18). Побег из пода в ноду, затем из user namespace через уязвимость ядра даёт не просто uid `wom`, а root сервера. Варианты, которые надо выбрать (**открыто**, принятым риск не считается):
1. Второй rootless‑демон под отдельным uid без sudo, с собственным data‑root и сокетом; оркестратор держит два сокета, kind работает только на втором. Работы на сервере под root, правка конфигурации оркестратора и runtime.
2. `PodSecurity restricted` на кластерах, где сценарий не требует привилегий (флаг `cluster.allowPrivileged` в `scenario.yaml`, который показывается модератору); часть сценариев каталога (`hostNetwork`, `privileged`, `hostPath`) его потребует.
3. Kind в VM (ADR‑0001, вариант c; `/dev/kvm` на сервере есть). Самый надёжный, самый большой.
Минимальное действие уже сейчас, не требующее кода: снять `NOPASSWD` sudo у `wom` (`docs/runbook-prod-install.md`).
