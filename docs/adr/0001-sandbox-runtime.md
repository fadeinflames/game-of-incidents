# ADR‑0001. Runtime песочниц

- Статус: **принято** (2026‑09‑29, вариант (a); дополнение по read‑only rootfs — по требованию к риску R‑4)
- Дата: 2026‑09‑29
- Роли: техлид, platform, security

## Контекст

Пользователь получает root‑shell в окружении, которое намеренно сломано, и чинит его. Требования (бриф, 4.2): не добраться до хоста, соседних сессий и внутренней сети платформы; никаких `--privileged`, docker socket, host network; сеть без выхода в интернет по умолчанию; лимиты CPU/RAM/PIDs/диска; старт ≤ 10 с; один VPS и один человек в эксплуатации.

Принято (7.3): VM‑изоляция с первого дня не нужна. Аудитория v1 — внутренняя команда (допущение 7.2), то есть пользователи не враждебны, но платформа должна выдерживать и ошибку, и любопытство.

## Варианты

| Вариант | Старт | Плотность | Изоляция | Что умеет сценарий | Эксплуатация одним человеком |
|---|---|---|---|---|---|
| (a) Docker с харднингом: user namespaces, seccomp по умолчанию, `no-new-privileges`, урезанные capabilities, cgroup‑лимиты, `internal` сеть | ~1 с при прогретом образе | высокая (десятки на 8 ГБ) | общее ядро с хостом; escape = уязвимость ядра или ошибка конфигурации | процессы, файлы, сеть внутри контейнера, nginx/PostgreSQL/cron; **не** systemd, модули ядра, диски, iptables без `NET_ADMIN` | самая простая, всё штатное |
| (b) gVisor (`runsc`) как runtime для тех же контейнеров | ~1–2 с | высокая | своё «ядро» в user space, ядро хоста почти не видно | как (a), но часть syscall/инструментов работает иначе (`strace`, `perf`, некоторые sysctl) — нужно проверять каждый сценарий | установка `runsc` на хост + одна строка в `daemon.json`; сложнее отлаживать |
| (c) Firecracker microVM | секунды при готовом rootfs | средняя | отдельное ядро | всё, включая systemd и диски | свой оркестратор сетей/rootfs/снапшотов — большая работа для одного человека |
| (d) Полные VM (libvirt/QEMU) | десятки секунд | низкая (единицы на 8 ГБ) | отдельное ядро | всё | тяжело, дорого по ресурсам |

## Решение

**Начать с (a)**, спроектировать `RuntimeProvider` так, чтобы (b) включалось конфигом, а (c) — отдельной реализацией интерфейса. Параметры харднинга для (a) — обязательный минимум с самого начала, а не позднее дополнение:

- Docker daemon: `userns-remap` включён (root в песочнице = непривилегированный uid на хосте); `live-restore` включён (рестарт демона не убивает сессии).
- Контейнер: `--cap-drop ALL` + явный allow‑list capabilities из сценария (по умолчанию `CHOWN, DAC_OVERRIDE, FOWNER, FSETID, KILL, SETGID, SETUID, NET_BIND_SERVICE, SETPCAP`); seccomp — профиль Docker по умолчанию; `--pids-limit`, `--cpus`, `--memory`, `--memory-swap = memory` из `environment.resources`.
- Пользователь в песочке (решено 2026‑09‑30): обычный пользователь `oncall` с passwordless `sudo`, «как на настоящем сервере». Следствие: `no-new-privileges` для песочниц **выключен**, потому что этот флаг запрещает setuid‑переход и ломает `sudo`. Потеря защиты минимальна: root внутри и так задуман, а bounding set capabilities контейнера остаётся урезанным, поэтому даже root не получит `SYS_ADMIN`, `NET_ADMIN` и прочее вне allow‑list. Для сценариев без `sudo` флаг можно включить обратно полем `environment.shell.sudo: false`.
- **Корневая ФС только для чтения** (`ReadonlyRootfs: true`) — требование по риску R‑4: пользователь не может ставить пакеты и менять бинарники в `/bin`, `/sbin`, `/usr`, `/lib`. Записываемые пути объявляет сценарий (`environment.writable`, по умолчанию `/etc`, `/var`, `/root`, `/home`, `/srv`); для каждого создаётся анонимный volume, который Docker при старте заполняет содержимым образа, поэтому конфиги в `/etc` редактируемы, а `/usr/bin` — нет. `/tmp` и `/run` — tmpfs с лимитом размера. Перемонтировать `/` в rw нельзя без `CAP_SYS_ADMIN`, которого нет. Из образов сценариев удаляются `apt`, `apk`, `dpkg`, `pip` (линтер v2 проверяет их отсутствие), выхода в интернет нет, так что установка пакетов невозможна ни одним из путей.
- Известное ограничение (проверено 2026‑09‑30): `/etc/hosts`, `/etc/hostname`, `/etc/resolv.conf` Docker подставляет отдельными bind‑mount'ами и при read‑only rootfs они неизменяемы даже внутри записываемого `/etc`. Сценарии про DNS должны использовать свой resolver внутри песочки (например, `dnsmasq` с конфигом в `/etc/dnsmasq.d`), а не правку `resolv.conf`.
- Машина разработчика: песочницы и платформа работают в **rootless‑демоне Docker** (`$XDG_RUNTIME_DIR/docker.sock`), а не в системном демоне. Rootless даёт user namespace по определению (root в контейнере = пользователь, под которым работает rootless‑демон) и не требует `userns-remap` на системном демоне, который нельзя трогать. На проде эквивалент — либо тот же rootless, либо `userns-remap` на выделенном демоне; решается на этапе выкладки на сервер.
- Сеть: на каждую сессию своя bridge‑сеть с `internal: true` (нет маршрута наружу); `egress: allowlist` реализуется позже через отдельный egress‑прокси, на начальном этапе только `none`. Никаких published портов: к сервисам внутри песочки обращается только оркестратор по IP контейнера (для грейдера и health).
- Диск: лимит записи в контейнерный слой через `--storage-opt size=` требует overlay2 на xfs с `pquota`; это фиксируется как требование к разметке VPS в ADR‑007. До этого — лимит через tmpfs на записываемых путях сценария (`/var/log`, `/var/lib/postgresql`) и мониторинг.
- Хост: docker socket недоступен из песочниц; оркестратор — единственный процесс с доступом к сокету.
- Запрещено на уровне кода `RuntimeProvider` (не конфигом): `privileged`, `network_mode: host`, монтирование путей хоста, `cap_add: SYS_ADMIN`.

Интерфейс (черновик, TypeScript):

```ts
interface RuntimeProvider {
  create(spec: SandboxSpec, labels: Record<string, string>): Promise<SandboxHandle>;
  exec(h: SandboxHandle, cmd: string[], opts: { tty: boolean; stdin?: boolean; user?: string }): Promise<ExecStream>;
  resize(exec: ExecStream, cols: number, rows: number): Promise<void>;
  inspect(h: SandboxHandle): Promise<SandboxStatus>;      // running | exited | missing
  destroy(h: SandboxHandle): Promise<void>;
  list(labelSelector: Record<string, string>): Promise<SandboxHandle[]>;  // для reconciler
}
```

## Последствия

- Плюс: старт песочницы укладывается в SLO ≤ 10 с с большим запасом; плотность ≥ 10 сессий на 8 ГБ.
- Плюс: миграция на gVisor — конфиг, не код; на Firecracker — новая реализация интерфейса.
- Минус (принимаемый риск): общее ядро. Митигация — `userns-remap`, seccomp, cap‑drop, свежее ядро на VPS с автообновлениями, внутренняя аудитория. Security фиксирует это в threat model как R‑1.
- Минус: сценарии с systemd невозможны; сервисы в образе стартуют через `entrypoint` (supervisord или простой скрипт), а `service nginx restart`‑подобные команды работают через SysV‑скрипты пакетов. Проверяется на первом сценарии.
- Минус: `userns-remap` ломает bind‑mount файлов с хоста с неправильными uid; мы bind‑mount не используем (артефакты копируются через `docker cp`/exec).

## Принятое решение

2026‑09‑29: вариант (a) принят. Риск общего ядра (R‑1) принят: машина под платформу выделенная и для разработки, её потеря допустима. Дополнительное требование: жёстко запретить установку пакетов и запись в каталоги с бинарниками — реализовано через read‑only rootfs выше, обязательное с самого начала.
