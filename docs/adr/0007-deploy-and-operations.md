# ADR‑0007. Деплой и эксплуатация

- Статус: **принято** (2026‑09‑29), актуализировано 2026‑10‑11
- Роли: техлид, platform, security, SRE платформы

## Контекст

Нужен один Linux-сервер, Docker, деплой одной командой, TLS, бэкап БД и обновление без потери активных сессий. Нужно, чтобы платформу мог поставить любой человек.

## Решение 1. Compose + systemd + Caddy

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Docker Compose + systemd-unit + Caddy** | один файл compose, автоматический TLS (Let's Encrypt) в Caddy, WebSocket проксируется без настройки, конфиг Caddy короткий | Caddy менее распространён, чем Nginx |
| Docker Compose + Nginx + certbot | привычно | ручной цикл TLS, отдельная настройка WebSocket |
| Traefik | динамика по меткам | лишняя магия для трёх сервисов |
| k3s | см. ADR‑0003 | отклонено там же |

Состав `deploy/`: `docker-compose.prod.yml` (оверлей: `caddy`, `web`, `orchestrator`, `db`; наружу опубликован только Caddy на 80/443), `Caddyfile` (домен → `web:3000`, `/ws/term/*` → `orchestrator:8080`), `wom.service` (пользовательский юнит systemd, поднимает стек при загрузке), `backup.sh` и юниты таймера, `healthcheck.sh` и `hostwatch.sh` (наблюдение), `db-roles.sh` (отдельная роль PostgreSQL для web).

## Решение 2. Rootless-демон Docker

Платформа и все песочницы живут в rootless-демоне Docker сервисного пользователя `wom` (без sudo). Это основная граница безопасности (ADR‑0001, `docs/threat-model.md`). Следствия:

- `live-restore` в rootless практически не работает: рестарт самого демона завершает все сессии; рестарт оркестратора их не трогает, терминалы переподключаются.
- Лимиты памяти и процессов действуют, только если пользователю делегированы cgroup v2 контроллеры `memory` и `pids` (делает `host-setup.sh`).
- Портовый драйвер `slirp4netns` сохраняет адрес клиента (нужен для лимитов по адресу).
- Том под data-root (xfs, отдельный loop-файл или раздел) изолирует переполнение песочницами от корня.

## Решение 3. Установка и обновление скриптами

- `scripts/provision/provision.sh` с машины администратора ставит голый хост одной командой (`host-setup.sh` от root, `app-setup.sh` от `wom`); идемпотентен, поддерживает Debian 13 и Ubuntu 24.04, режим без домена по IP.
- `scripts/deploy.sh [sha]`: блокировка от параллельного запуска; образы платформы и сценариев; `npm ci --ignore-scripts`; линт сценариев; сборка compose; предзагрузка образов; ожидание конца подъёмов сессий; проверка egress-guard; предеплойный дамп БД; миграции и сид; рестарт стека; health; перезапуск Caddy при изменении `Caddyfile`. На время выкатки новые сессии не принимаются (drain), по выходу режим всегда выключается. Логи шагов в `~/.cache/wom-deploy/`.
- Откат кода: `./scripts/deploy.sh <sha предыдущего коммита>`; при несовместимой миграции сначала восстанавливается предеплойный дамп. Образов `:previous` и `rollback.sh` нет.
- `make verify` (`scripts/verify.sh`) — проверка перед выкладкой (одноразовая PostgreSQL, типы, тесты, тесты скриптов, лицензии, `bash -n`, shellcheck). CI проверяет только pull request и не деплоит.

## Решение 4. Наблюдение и бэкапы

- `GET /api/health`: `{"ok":…,"checks":{"db","orchestrator","disk","egress"}}`; `/metrics` и профиля мониторинга нет. Внешняя проверка `deploy/healthcheck.sh` (cron на другой машине) и локальный сторож `deploy/hostwatch.sh` шлют сообщения в Telegram.
- `deploy/backup.sh`: ночной `pg_dump` в `/srv/backups`, 14 копий; дамп проверяется до ротации (код возврата, `gunzip -t`, размер, завершающая строка), при ошибке хорошие дампы не вытесняются; права 600/700; дамп не шифруется (опционально `BACKUP_AGE_RECIPIENT` шифрует копию `.env`). Копию за пределы сервера забирает другая машина (rsync).
- Диск: порог отказа в новых сессиях 85 %, аварийная остановка 93 %. БД может лежать на отдельном каталоге (`PGDATA_MOUNT`).

## Требования к серверу

Debian 13 или Ubuntu 24.04 LTS, x86‑64, systemd, cgroup v2; 2+ CPU и 8+ ГБ RAM (рекомендуется 8 CPU и 32 ГБ для многих параллельных кластерных сессий; ёмкость подбирается по ресурсам машины); 40+ ГБ свободного места; открытые порты 22, 80, 443; доступ root по ssh-ключу для установки.

## Последствия

- Плюс: один понятный `provision.sh`/`deploy.sh`, понятный человеку и AI; путь к microVM не закрыт.
- Минус: рестарт демона Docker завершает сессии; бэкапы обязаны уходить за пределы машины, иначе бэкапа нет.
- Подробности и команды: `docs/runbook-prod-install.md`.
