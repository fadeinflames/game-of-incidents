# ADR‑0002. Веб‑терминал

- Статус: **принято** (2026‑09‑29, вариант D)
- Дата: 2026‑09‑29
- Роли: техлид, frontend, backend, security

## Контекст

Терминал в браузере должен открываться только владельцу сессии, работать за reverse‑proxy по WSS, поддерживать ресайз, вставку, IME, несколько вкладок в одно окружение, переподключение после обрыва, и в будущем — запись сессии и read‑only наблюдение ведущим (7.6/7.7).

Подтверждённые факты из брифа (2.4): ttyd — C, любая CLI‑программа через браузер, минимум конфигурации; GoTTY — Go, один бинарник, умеет изолированные docker‑окружения, используется в SadServers; Wetty — Node.js + xterm.js, локальный shell и SSH; xterm.js + свой PTY‑бэкенд — максимум контроля.

## Варианты

| Вариант | Аутентификация владельца | Несколько вкладок | Запись / наблюдение | За reverse‑proxy | Что добавляет в эксплуатацию |
|---|---|---|---|---|---|
| A. ttyd — по процессу на сессию, каждый на своём порту/пути, `ttyd docker exec -it <ctr> bash` | только basic‑auth или проксирование с проверкой cookie на прокси; связать «этот ttyd = этот пользователь» надо снаружи | ttyd умеет несколько клиентов к одному процессу, но это один и тот же PTY (общий экран), не независимые вкладки | нет встроенной записи; наблюдение = тот же общий экран (нет read‑only) | работает по WS, нужен path‑routing на каждый экземпляр | ещё один бинарник и N процессов, которые тоже надо reconcile'ить |
| B. GoTTY — аналогично A | как A | как A | нет | как A | как A; проект менее активен, чем ttyd (нужно проверить) |
| C. Wetty | своя auth или прокси | по вкладке на подключение | нет | работает | Node‑процесс, ориентирован на SSH/локальный shell, а не на `docker exec` |
| D. **xterm.js во фронте + WebSocket‑шлюз внутри оркестратора**, который открывает `docker exec` с TTY через Docker Engine API (`dockerode`: `container.exec` → `start({hijack: true, stdin: true})`, `exec.resize`) | одноразовый терминальный токен, выданный web‑приложением после проверки владельца сессии; шлюз проверяет токен и `sessionId` перед attach | каждая вкладка — отдельный `exec` в тот же контейнер | шлюз видит поток байтов: запись в asciicast‑формат и read‑only broadcast — прямая надстройка | один WS‑endpoint `/ws/term/:sessionId`, обычный path‑routing | код, который мы пишем сами (~200–300 строк на старте), но никаких дополнительных процессов |

## Решение

**D.** Терминальный шлюз — часть оркестратора (ADR‑0003), не отдельный сервис.

Протокол клиент ↔ шлюз (минимальный, бинарные и текстовые фреймы):

- клиент открывает `wss://host/ws/term/<sessionId>?token=<one-time>`; шлюз проверяет токен (выдан web, привязан к `sessionId` и `userId`, живёт 60 с, одноразовый), затем создаёт `exec` с `Tty: true`, `Cmd: [shell из environment.shell]`, `User: root`;
- бинарные фреймы — байты PTY в обе стороны; текстовый JSON‑фрейм `{"type":"resize","cols":..,"rows":..}` — ресайз; `{"type":"ping"}` — keepalive за прокси;
- обрыв WS завершает `exec`; окружение остаётся. Переподключение = новый `exec` (новый shell). Сохранение shell‑состояния между обрывами в MVP не делаем; если понадобится, внутри образа ставится `tmux`, а шлюз запускает `tmux new -A -s main`.

Фронт: `@xterm/xterm` + `@xterm/addon-fit` + `@xterm/addon-web-links`; вставка и IME обрабатываются xterm.js.

Запись сессии (7.7, выключена в MVP): шлюз пишет вывод в файл asciicast v2 рядом с сессией, включается флагом сценария и явным согласием в UI.

## Последствия

- Плюс: одна точка контроля доступа к терминалу, никакие порты песочниц наружу не публикуются.
- Плюс: multiplexing, запись и наблюдение — надстройки над одним потоком.
- Минус: свой код на критичном пути; покрывается integration‑тестом «открыть WS с неверным токеном → 401, с верным → получить приглашение shell».
- Минус: ресайз идёт через Docker API, а не через PTY напрямую; это штатный вызов `exec resize`, задержки незаметны.

## Принятое решение

2026‑09‑29: D принят.

## Спайк (сделан)

Прототип (удалён из репозитория после проверки) показал:

- харднутая песочница (read‑only rootfs, cap‑drop, лимиты, internal‑сеть) создаётся и стартует за **479 мс** (образ `alpine:3.20`, прогрет);
- WebSocket‑upgrade с неверным токеном → `401`; с одноразовым токеном → shell в xterm.js, ввод, вывод и ресайз работают;
- в терминале подтверждено: `uid=0`, `touch /usr/bin/evil` → Read‑only file system, запись в `/etc/wom.conf` работает, `wget 1.1.1.1` → Network unreachable, `ps` видит 5 процессов;
- `SIGINT` шлюзу → контейнер, сеть и анонимные тома удалены (0 остатков), rootful‑контейнеры не затронуты.
