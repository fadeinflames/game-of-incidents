# ADR‑0006. Стек приложения и структура репозитория

- Статус: **принято** (2026‑09‑29)
- Дата: 2026‑09‑29
- Роли: техлид, backend, platform

## Контекст

`wom-games` — работающее приложение на Next.js 16 + Prisma 6 + PostgreSQL 16 с авторизацией, каталогом, импортом и leader mode. Game of Incidents добавляет к нему оркестрацию живых песочниц, терминал и грейдер.

Ограничения проекта:

1. Код живёт в отдельном репозитории и отдельной папке.
2. Сопровождать код будет AI‑ассистент, а не команда инженеров. Значит, главный критерий — **предсказуемость для нейросети**: один язык, одна система типов, минимум «магии», явные границы модулей, воспроизводимые команды.
3. Один сервер, один человек в эксплуатации.
4. Переиспользовать `wom-games`, а не переписывать.

## Решение 1: как перенести код из `wom-games` в отдельный репозиторий

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Начать `wom-platform` как копию `wom-games` с историей (`git fetch` из `wom-games`, затем развивать) | История коммитов и авторство сохранены; переносится всё сразу; `git log -S` продолжает работать для старого кода | Тянем Railway‑артефакты, leader mode и 18 Kubernetes‑сценариев, которые MVP не использует; больше кода на входе — больше риска, что «не заведётся» |
| B. Новый репозиторий с нуля, модули копируются файлами по мере надобности | Чистая и маленькая структура; каждый файл в репозитории понятен и нужен | Теряется история; требуется дисциплина «копировать, а не переписывать» для проверенных модулей (auth) |
| C. Monorepo, где `wom-games` — git submodule / пакет | Формально «переиспользование» | Submodule ломает сопровождение одним человеком и AI; `wom-games` не оформлен как пакет |

**Выбор: B** (принято 2026‑09‑29: историю не импортировать, начать с нуля с чего‑то простого, что заведётся без проблем). `wom-platform` начинается пустым; из `wom-games` копируются файлами только те модули, которые нужны на текущем этапе (на начальном этапе это `src/lib/auth.ts`, `http.ts`, `rate-limit.ts`, `validation.ts` и модели `User`/`Session`). Leader mode, паки и галерея переносятся позже и только если к тому моменту они всё ещё нужны. Приоритет — минимальный работающий контур, а не полнота переноса.

## Решение 2: структура приложения

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Всё внутри Next.js (route handlers говорят с Docker) | Один процесс | Docker socket оказывается в процессе, который отдаёт публичный HTTP — Security против; долгоживущие WebSocket и фоновые reconcile‑циклы плохо живут в serverless‑модели Next.js |
| B. Next.js (UI + API продукта) **+ отдельный сервис‑оркестратор на TypeScript/Node** в том же репозитории; общий Prisma‑клиент и типы через workspace‑пакет | Один язык; Docker socket только у оркестратора; WebSocket‑шлюз терминала и reconcile живут в нормальном long‑running процессе; всё ещё один `docker compose up` | Два процесса вместо одного; нужен внутренний контракт Next.js ↔ оркестратор |
| C. Next.js + оркестратор на Go | Один статический бинарник, удобно для агента в песочнице | Второй язык и вторая система типов; для AI‑сопровождения это удвоение контекста; предпочтений по языку нет, значит платить за Go нечем |

**Выбор: B.** Оркестратор — Node 22 + TypeScript, HTTP + WebSocket (конкретные библиотеки фиксируются в ADR‑002/003), доступ к Docker через `dockerode` по unix‑socket. Next.js к Docker не подключается никогда. Go допускается позже только для агента внутри песочницы, если ADR‑004 докажет необходимость.

Итоговая раскладка репозитория:

```
wom-platform/
  apps/web/            # Next.js (наследник wom-games: auth, каталог, импорт, leader mode, UI сессии)
  services/orchestrator/  # сессии, RuntimeProvider, терминальный шлюз, грейдер‑раннер, reconciler
  packages/db/         # Prisma schema + client, общие типы
  packages/scenario/   # схема v2, валидатор, CLI `wom scenario lint|run`
  scenarios/           # библиотека сценариев (каждый — папка)
  deploy/              # compose, Caddy/Traefik, systemd, скрипты бэкапа
  docs/                # architecture, adr, threat-model, runbook
```

Инструменты: npm workspaces (без pnpm/turbo, чтобы не добавлять слоёв), Vitest для unit/integration, Playwright для e2e критичного пути, GitHub Actions для CI. Версии фиксируются в `package-lock.json`.

## Последствия

- Плюс: репозиторий содержит только то, что реально работает и покрыто тестами; нейросети проще сопровождать маленький явный код, чем большой унаследованный.
- Плюс: граница «публичный HTTP ↔ Docker» проходит между процессами, что упрощает threat model.
- Минус: история изменений `wom-games` не наследуется; при копировании модуля в комментарии к файлу указывается источник (`// Ported from fadeinflames/wom-games <commit> <path>`).
- Минус: нужен внутренний контракт между web и оркестратором (REST + общий секрет внутри compose‑сети) — фиксируется в ADR‑003.
- Минус: leader mode и 18 текстовых сценариев `wom-games` в MVP отсутствуют; возвращаются отдельным этапом.

## Принятое решение

Вариант B для репозитория и вариант B для структуры приложения приняты 2026‑09‑29: не импортировать историю, а сделать кейсы с нуля, плюс‑минус простые, чтобы всё заводилось без проблем. Статус ADR: **принято**.

## Реализация и отклонения (дополнение 2026‑10‑01)

- **CI только проверяет код.** Он (`.github/workflows/ci.yml`) прогоняет проверки на pull request'ах и на `main`, ничего не выкладывает и не использует секретов. Доставка — `scripts/deploy.sh` (ADR‑0007): сервер сам забирает `main` и собирает образы. Полный набор проверок запускается вручную: `make typecheck`, `make test`, `make lint`, `make regress`, `make e2e`.
- **Раскладка репозитория шире, чем в схеме выше.** Кроме `apps/web`, `services/orchestrator`, `packages/db`, `packages/scenario`, `scenarios`, `deploy`, `docs` есть `packages/runtime` (интерфейс `RuntimeProvider` и реализации Docker, kubernetes/kind, fake; общий харднинг для оркестратора и CLI), `images/` (образы платформы: `tools`, `egress-guard`, `sysv-shims`), `scripts/` (`deploy.sh`, `prepull-images.ts`), `agent-skill/wom-scenario-author` (инструкция для LLM), `schemas/` (JSON Schema формата v2).
- **Что скопировано из `wom-games`:** авторизация (`auth.ts`, `http.ts`, `rate-limit.ts`, `validation.ts`, модели `User` и `Session`), форма логина. Leader mode, паки и галерея не переносились; 18 текстовых сценариев `wom-games` вернулись как живые сценарии на kind.
- **Оркестратор запускается через `tsx` без сборки** (TypeScript исполняется напрямую, devDependencies остаются в образе): осознанный компромисс начального этапа, не пересматривался.
- **Тесты.** Vitest: юнит‑ и интеграционные тесты оркестратора (интеграционные пропускаются без `DATABASE_URL`, их надо гонять на отдельной базе: они завершают активные сессии), тесты `packages/runtime` и `packages/scenario`. У `apps/web` юнит‑тесты маршрутов и библиотек (Vitest).
