# ADR‑0009. Загрузка сценариев пользователями и модерация

- Статус: **принято** (2026‑09‑30: загружать может любой пользователь, проект открытый, модерация обязательна)
- Роли: техлид, backend, security

## Контекст

Нужен аналог SadServers с возможностью загружать свои сценарии (как это было с skill'ом в `wom-games`), причём загружать может любой зарегистрированный пользователь, а проект планируется открыть. Сценарий содержит Dockerfile и скрипты, то есть **чужой код, который должен выполниться на нашем сервере**: сборка образа и регресс в песочнице.

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Полный автомат: загрузил → сборка → регресс → модератор публикует | быстрая обратная связь автору | чужой Dockerfile собирается на хосте без участия человека: `RUN` выполняется в rootless‑демоне, но с egress и ресурсами хоста; спам заявок = DoS на сборках |
| B. **Статика автоматом, исполнение по кнопке модератора** | ни одна строка чужого кода не выполняется, пока человек не посмотрел заявку; спам не тратит CPU | автор ждёт модератора, чтобы узнать результат регресса |
| C. Только ручная загрузка администратором | максимально безопасно | противоречит цели «загружать может кто угодно» |

## Решение

**B.** Поток:

1. Автор загружает zip папки сценария на странице «Мои сценарии» (≤ 5 МБ, ≤ 200 файлов, ≤ 20 МБ распакованных; пути с `..`, абсолютные и `\` отклоняются).
2. Web распаковывает во временный каталог, прогоняет загрузчик и линтер формата v2 (статика: схема, файлы, POSIX sh, JSON грейдера, харднинг, tmpfs, пространство имён тега образа `wom-scenario/<slug>:…`). Результат сразу виден автору. Заявка со статусом `UPLOADED` или `LINT_FAILED`, архив хранится в БД.
3. Slug принадлежит первому автору: заявка с чужим slug отклоняется на входе.
4. Администратор на странице «Заявки» нажимает «Проверить»: оркестратор ставит заявку в очередь (по одной), собирает образ в rootless‑демоне (таймаут 10 минут) и гоняет тот же регресс, что и CLI (`runScenarioTest` с реальным `RuntimeProvider`, включая пробы харднинга). Статусы `TESTING → PASSED | FAILED`, отчёт и лог сборки видны автору и модератору. Заявки, зависшие в `TESTING` при рестарте оркестратора, возвращаются в очередь.
5. «Опубликовать» доступно только для `PASSED`: запись сценария создаётся из того же `ImportRecord`, что и тестировался, с `authorId`. «Отклонить» требует комментарий автору.

## Безопасность (дополнение к threat model)

- **T‑16 / R‑8. Сборка чужого Dockerfile на хосте.** `RUN`‑шаги выполняются в rootless‑демоне (user namespace) с egress. Митигация: запуск только после решения модератора, очередь по одной, таймаут; позже — лимиты памяти и CPU на сборку и запрет egress через egress‑прокси. Для внутренней команды принималось; для публичной регистрации вопрос открыт (R‑8 в `docs/threat-model.md`, раздел «Дополнение 2026‑10‑01» ниже).
- Регресс присланного сценария идёт в той же харднутой песочнице, что и обычные сессии (read‑only rootfs, cap‑drop, лимиты, без egress для Linux‑хостов).
- Архив хранится в БД как bytes; на диск попадает только во временный каталог на время проверки и удаляется.
- Rate‑limit на загрузку: 3 в минуту с IP.

## Последствия

- Плюс: любой может прислать сценарий, при этом ни одна строка чужого кода не выполняется без человека.
- Минус: латентность обратной связи по регрессу зависит от модератора. Смягчение: e‑mail/Telegram уведомления модератору — после появления почтового сервера.
- Плюс: skill v2 (`agent-skill/wom-scenario-author/SKILL.md`) генерирует всю папку под формат, автор проверяет локально `wom scenario lint|test` до загрузки.

## Дополнение 2026‑10‑01: страница заявки для модератора и ограничения сборки

Сверено с кодом после первой волны исправлений по аудиту. Решение B не менялось; изменился порядок работы модератора и добавлены ограничения.

- **Модератор видит заявку целиком до запуска чужого кода.** Действия «Проверить», «Опубликовать», «Отклонить» убраны из списка `/admin/submissions` и остались только на странице заявки `/admin/submissions/[id]`. Список ведёт на неё кнопкой «Открыть заявку: файлы и действия». На странице заявки: все файлы архива (текстовые до 64 КБ каждый, суммарно до 1 МБ на страницу; `Dockerfile` и `*.sh` раскрыты сразу, остальные — списком с размерами), подсказки отдельным блоком, отчёты lint и теста, ссылка «Скачать zip» (`GET /api/admin/submissions/[id]/archive`, только админ). Если `slug` уже есть в каталоге, показывается построчный diff с опубликованной версией: метаданные, подсказки, бриф, разбор, этапы помощи, окружение с манифестами и три скрипта. Расхождение: если в заявке `gmScriptJson` или `environmentJson` равны `null`, публикация поле не очищает (`upsert` с `?? undefined`), а diff покажет удаление.
- **Распаковка.** Лимиты проверяются по центральному каталогу архива до распаковки: не больше 5 МБ архив, 200 файлов, 2 МБ на файл и 20 МБ всего; `zip64`, шифрованные архивы и методы сжатия кроме `stored` и `deflate` отклоняются; распаковка обрывается, когда выход превысил заявленный размер. Тесты — `packages/scenario/test/archive.test.ts`.
- **Линтер заявок строже.** Базовые образы `FROM` разрешены только из `debian:bookworm-slim`, `python:3.12-alpine`, `alpine:3.20` (и стадий того же `Dockerfile`; `COPY --from` и `RUN --mount from=` с чужим образом, директива `# syntax=` — ошибки `build-escapes`); образы из `k8s/*.yaml` обязаны быть перечислены в `environment.images`; `cluster.nodeImage`, ссылки на образы и capabilities проверяются по шаблонам; предупреждения для грейдеров с `psql` без `-X` и `curl` без `-q` (ADR‑0004).
- **Сборка чужого Dockerfile.** По‑прежнему в rootless‑демоне прода, с сетью и без лимитов CPU, памяти и диска: `RUN` и `ADD <url>` выполняются от uid `wom`. Добавлены жёсткий таймаут `SUBMISSION_BUILD_TIMEOUT_MS` (10 минут; `SIGTERM`, через 10 с `SIGKILL`) и хвост лога 64 КиБ вместо накопления всего вывода. Изоляция сборки (отдельный демон или хост, сборка в ограниченном контейнере, лимит размера образа, `--network=none` с зеркалом пакетов) не сделана: **решение по R‑8 открыто**. Список разрешённых `FROM` — защита в глубину, а не граница.
- **Кабинет автора.** На `/author` вместо путей приватного репозитория — ссылка на скачивание инструкции для LLM (`GET /api/author/skill`, файл `agent-skill/wom-scenario-author/SKILL.md`, нужен вход) и шаги «скачай, заархивируй, исправь замечания из заявки». Образцы сценариев и команда `wom` находятся в репозитории проекта. Пользователям Windows: `Compress-Archive` из PowerShell 5.1 пишет пути с обратными слэшами, такой zip отклоняется; подойдёт `tar -a -cf`.
- **Не реализовано и ждёт решения.** Уведомления о новых заявках (в коде нет ни одной отправки в Telegram, хотя `deploy/healthcheck.sh` умеет); заметить заявку можно только по счётчику «ждут» на `/admin`. Роль модератора отдельно от админа: `User.role` принимает только `user` и `admin`, «Сделать админом» даёт полный доступ. Предложения аудита: уведомление в Telegram Bot API при новой заявке `UPLOADED` и ежедневный дайджест «ждут: N», затем роль `moderator` с доступом только к `/admin/submissions` и `/admin/scenarios`. Решение не принято; пока модерирует один человек.
- **Лимиты заявок.** Rate‑limit загрузки 3 в минуту с адреса клиента. Лимита числа заявок на пользователя и очистки старых архивов (`archive` до 5 МБ в БД, входят в каждый дамп) нет.
