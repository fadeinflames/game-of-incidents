## Что было сломано

После ночного сброса `access-api` отдавал девяти клиентам статус «бюджет исчерпан», измеренный ещё в закрытом периоде. В базе у них расход ноль.

- Статус доступа лежит в Redis (`access:<клиент>`). Ночная задача `monthly-reset` обнулила счётчики и удалила все статусы, чтобы API посчитал их заново. Эта часть отработала правильно.
- Узлы шлюзов досылают записи об использовании с опозданием: записи последних часов закрытого периода приходят ещё сутки. Если узел к тому моменту уже отказывал клиенту, запись несёт состояние `budget_state: exhausted`.
- `budget-worker` применяет такую запись в два шага. Расход он относит на закрытый период, и это верно. Состояние из записи он пишет в `access:<клиент>` как есть, с датой до сброса. Так только что очищенный статус возвращался, и API отдавал его шлюзам.
- От этого была защита. В `budget-worker` 2.8.0 появилась настройка `access.discard_state_before_reset`: состояние, измеренное до последнего сброса, не применять. Неделю назад её включили в `/etc/settingsd/namespaces/budget-worker.toml`, но написали `yes` вместо `true`. В TOML такого значения нет, файл перестал разбираться целиком.
- `settingsd` в этом случае не падает. Он пишет одну строку `WARN ... not loaded (Invalid value (at line 13, column 30)); serving built-in defaults` и раздаёт значения по умолчанию, где защита выключена. Воркер получил `false` и честно напечатал это в первой строке своего лога.
- Пострадали только те, кто исчерпал бюджет в закрытом периоде: девять клиентов из шестидесяти. Остальные работали, поэтому вместо аварии была тонкая струйка обращений.
- Отдельно от этого воркер отставал: в очереди `queue:budget-updates` ждали больше 6000 событий, самые старые полтора часа. Воркер берёт два события в секунду, шлюзы присылают почти одно, поэтому очередь убывала на 70 событий в минуту. В ней же стояли изменения бюджетов, отсюда жалоба клиента 1023.

## Как это диагностируется

1. `curl -s 127.0.0.1:8080/v1/access/1017`: `"allowed": false`, `"spent_cents": 5032`, `"cache": "hit"`, `"as_of"` вчерашним вечером. В базе (`sudo -u postgres psql -d budgets`) у того же клиента в `usage_current` расход 0 при лимите 5000, а период в `billing_periods` начался сегодня в 00:00. Ответ старше периода.
2. `redis-cli get access:1017` показывает то же и поле `source`: `gateway gw-1, seq ...`. Статус записал не API, а кто-то со слов шлюза. Для сравнения у клиента 1008 `source` равен `access-api`, дата сегодняшняя, расход 3075 при лимите 3000: его отказ настоящий.
3. `grep 1017 /var/log/budget-worker/worker.log`: `late record, posted to period ...` и сразу за ней `gateway gw-1 reports budget_state=exhausted (5032 of 5000) as of ..., access status saved: blocked`. Пишет воркер, из запоздавших записей.
4. Проверка на возврат: `redis-cli del access:1017`, API отвечает `allowed: true`, а обычно в пределах минуты отказ снова на месте. Удалять статус бесполезно, пока его кто-то пишет.
5. `/opt/budget/CHANGELOG`, версия 2.8.0: именно для этого есть `access.discard_state_before_reset`. Первая строка `settings` в логе воркера показывает `access.discard_state_before_reset=false`.
6. `grep discard /etc/settingsd/namespaces/budget-worker.toml` показывает, что настройку включали. `curl -s 127.0.0.1:8500/v1/settings/budget-worker` отдаёт `false`. Расхождение объясняет `/var/log/settingsd/settingsd.log`: строка `WARN` с номером строки и колонки, первая неделю назад, вторая при последнем запуске. Дата изменения файла совпадает с первой.
7. `redis-cli llen queue:budget-updates` и строка `queue ...: N events waiting, the oldest was queued M min ago` в логе воркера раз в минуту: очередь длинная и почти не убывает. `redis-cli lrange queue:budget-updates 0 5` показывает, что в ней лежит.

## Эталонное решение

Порядок такой: сначала защита, потом очередь, в конце уже записанные статусы.

```bash
# 1. Файл настроек снова разбирается; заодно воркеру разрешено брать больше событий за раз
sudo sed -i 's/^discard_state_before_reset = yes/discard_state_before_reset = true/; s/^batch_size = 2/batch_size = 500/' \
  /etc/settingsd/namespaces/budget-worker.toml
sudo service settingsd reload
tail -n 3 /var/log/settingsd/settingsd.log          # namespace budget-worker: 4 values from ...
curl -s 127.0.0.1:8500/v1/settings/budget-worker    # discard_state_before_reset: true, batch_size: 500

# 2. Воркер спрашивает settingsd раз в 15 секунд
grep 'settings changed' /var/log/budget-worker/worker.log
redis-cli llen queue:budget-updates                 # меньше чем за минуту доходит до нуля
grep -c 'state discarded' /var/log/budget-worker/worker.log

# 3. Устаревшие статусы: удаляются только ключи access:*, API посчитает их заново по базе
redis-cli --scan --pattern 'access:*' | xargs redis-cli del
curl -s 127.0.0.1:8080/v1/access/1017               # allowed: true, cache: miss
curl -s 127.0.0.1:8080/v1/access/1008               # allowed: false, бюджет этого периода исчерпан
```

Что здесь можно сделать иначе:

- Не зависеть от `settingsd` вовсе. В `/etc/budget-worker/worker.conf` есть секция `[overrides]`: строки `access.discard_state_before_reset = true` и `queue.batch_size = 500`, затем `sudo service budget-worker restart`. Грейдер принимает и этот путь, он проверяет результат. Именно так поступила компания в настоящем инциденте: её исправление перестало зависеть от сервиса настроек. Файл `settingsd` при этом всё равно стоит починить, иначе следующая настройка из него тоже не дойдёт.
- Удалять можно все ключи `access:*` разом, включая статусы тех, кто действительно исчерпал новый бюджет. Здесь это безвредно: на промахе кэша API считает статус по базе в том же запросе, и такой клиент не получает доступа ни на один запрос. Аккуратнее удалить только статусы с `as_of` раньше начала периода, но результат тот же.
- После разбора очереди `batch_size` можно вернуть к прежнему значению или оставить. В настоящей системе это решение о нагрузке на базу.

После разбора очереди меняются и честные статусы: клиенты 1019 и 1040 получают доступ, потому что их повышение бюджета наконец применено, а клиент 1026 теряет его, потому что уменьшил бюджет ниже уже потраченного.

## Ловушки

- **`FLUSHALL` или `FLUSHDB`.** Статусы пропадают, и на минуту всё выглядит починенным. Вместе с ними пропадают очередь с шестью тысячами событий (расход закрытого периода и изменения бюджетов), сессии личного кабинета и счётчик `meter:seq`, по которому шлюзы нумеруют записи. Вернуть это нечем. А отказ приходит обратно с первой же запоздавшей записью.
- **Удалить только ключи `access:*` и на этом закончить.** Через несколько секунд воркер доходит до следующей запоздавшей записи и пишет статус снова. За минуту отказ возвращается почти ко всем девяти.
- **Удалить очередь или вычистить из неё «плохие» записи.** Запоздавшая запись несёт не только устаревшее состояние, но и расход закрытого периода, по которому выставляется счёт. Грейдер сверяет номера записей: потерянные события он видит.
- **Перезапустить `access-api`, `budget-worker` или `settingsd`.** Статусы лежат в Redis и перезапуск переживают. `settingsd` после перезапуска читает тот же файл и пишет в лог ту же строку `WARN`.
- **Запустить `monthly-reset --force`.** Без ключа задача отказывается, и не зря. С ключом она обнуляет расход, накопленный с начала периода: клиенты, честно исчерпавшие новый бюджет, получают доступ, а начало периода сдвигается на текущую минуту. Статусы она тоже удаляет, но воркер возвращает их так же, как после ночного сброса.
- **Поднять лимит или обнулить расход в PostgreSQL руками.** На отказ это не влияет: API до базы не доходит, он отвечает из кэша. Зато данные о деньгах клиента теперь неверны.
- **Разогнать очередь и удалить статусы, не включив защиту.** Очередь опустеет, отказы пропадут, но шлюзы продолжают досылать записи закрытого периода, и отказ возвращается с первой из них. Порядок тоже важен: статусы удаляются после того, как защита дошла до воркера, иначе запись, применённая в промежутке, вернёт отказ.
- **Остановить `budget-worker`.** Писать устаревший статус становится некому, но и изменения бюджетов, и расход больше не применяются.

## Как было на самом деле

Сценарий сделан по мотивам инцидента GitHub 1 июля 2026 года. Компания опубликовала о нём только короткое сообщение на странице статуса, поэтому фактов немного.

Что сообщила компания:

- Примерно с 00:00 до 13:04 UTC часть клиентов Copilot, исчерпавших бюджет до месячного сброса, оставалась заблокированной в платном использовании после начала нового расчётного месяца, хотя их бюджеты были сброшены. Некоторые изменения бюджетов применялись дольше обычного.
- Затронуты были только клиенты с исчерпанным бюджетом, это ограничило масштаб.
- Причина в кэшировании при месячном сбросе: у части пользователей статус «бюджет исчерпан», относившийся ко времени до сброса, был сохранён заново и продолжал отдаваться.
- Защита от этого была подготовлена заранее, но не сработала: внутренний сервис конфигурации неправильно загрузил свои настройки.
- Исправление: выкатили изменение, которое отбрасывает устаревший статус и пересчитывает доступ по актуальным данным о бюджете независимо от той конфигурации. Накопившиеся обновления бюджетов разобрали.
- На будущее компания обещала сделать так, чтобы статус, посчитанный до сброса, не мог пережить сброс, добавить оповещение на такой сбой и увеличить мощность под месячный всплеск обновлений бюджетов.

Что в стенде придумано, потому что компания этого не раскрывала:

- Каким путём устаревший статус сохранялся заново. В стенде это запоздавшие записи шлюзов с состоянием внутри, которые воркер пишет в кэш. Как это было устроено у GitHub, неизвестно.
- Почему сервис конфигурации не загрузил настройки. Значение `yes` в TOML-файле и молчаливый переход на значения по умолчанию придуманы для стенда.
- Почему копилась очередь. В стенде у воркера просто маленькая пропускная способность, и её можно поднять настройкой.
- Все имена, таблицы, числа и сама предметная область (распознавание документов, 60 клиентов, 9 затронутых).
- Исправление в стенде делается настройкой, а не выкаткой нового кода: код в `/opt` только для чтения. Локальная секция `[overrides]` стоит на месте того, что компания назвала независимостью от конфигурации.

## Чему учит

- **Смотри на возраст ответа, а не только на ответ.** Поля `as_of` и `source` в статусе сократили поиск до двух команд. Кэш без отметки «когда и кем посчитано» пришлось бы разбирать вслепую.
- **Событие, которое несёт готовое состояние, опасно тем, что может опоздать.** Применять чужое состояние можно, только сравнив его время с тем, что уже известно: с началом периода, с версией записи. Иначе старое событие перезапишет новую правду.
- **Очистка кэша ничего не чинит, пока жив тот, кто его наполняет.** Сначала источник, потом уже записанное. Иначе чистить придётся бесконечно.
- **Защита, которая включается настройкой, не работает, пока настройка не дошла.** Проверять надо не файл, а действующее значение у того, кто его использует: строку в логе сервиса, ответ сервиса настроек.
- **Молчаливый переход на значения по умолчанию превращает ошибку в файле в ошибку в поведении.** Одна строка `WARN` неделю лежала в логе, который никто не читал. Сервис настроек, не сумевший загрузить файл, должен говорить об этом так, чтобы услышали: оповещением, отказом принять изменение, проверкой при выкатке.
- **Общий Redis нельзя лечить `FLUSHALL`.** В одном экземпляре лежали кэш, который можно потерять, и очередь, которую терять нельзя. Одна команда не различает их.
- **Редкие события надо репетировать.** Сброс бывает раз в месяц, и защиту, написанную к нему, впервые проверил сам сброс.
