# Как подступиться

«Часть запросов отвечает 500» разбирается одной лестницей: **воспроизвести → понять, кого и что задело → прочитать ошибку дословно → найти, что изменилось → найти, откуда приложение берёт то, чего больше нет → исправить и проверить всё, а не один случай**. Спускайся сверху вниз и не перепрыгивай ступени.

## Воспроизведи ошибку и найди здорового соседа

```bash
for u in 1042 2042 3042; do
  for p in "" /tasks /feed; do
    echo "$(curl -s -o /dev/null -w '%{http_code}' localhost:8080/users/$u$p) /users/$u$p"
  done
done
```

Цикл спрашивает все три страницы у одного пользователя из каждого шарда и печатает код ответа. Смотри, у кого коды плохие и на каких страницах. Запомни одного пользователя, у которого страница ломается, и одного, у которого та же страница работает: дальше ты будешь их сравнивать. Жалоба поддержки называет одну страницу. Проверь, одна ли она на самом деле.

## Оцени масштаб по логу запросов

```bash
awk '{print $4, $5}' /var/log/board-api/access.log | sort | uniq -c
grep ' 500 ' /var/log/board-api/access.log | head -n 3
```

В `access.log` каждая строка это один запрос: время, страница, код ответа, шард. Первая команда считает, сколько каких кодов пришлось на каждый шард. Вторая показывает самые первые ошибки: запомни время первой, оно пригодится. Вопрос этого этапа: ошибки размазаны по всем пользователям или собраны в одном месте?

## Прочитай ошибку дословно

```bash
grep ' 500 ' /var/log/board-api/api.log | tail -n 4
```

Клиент получает просто `500`, а причину сервис пишет в свой лог: текст, который вернула база, и запрос, на котором она его вернула. Прочитай текст ошибки целиком. В нём есть имя объекта, которого базе не хватает, и имя таблицы. В запросе найди место, где это имя упоминается. Ошибок два вида: посмотри, чем они отличаются.

## Сравни больной шард со здоровым

```bash
sudo mysql board_s1 -e 'SHOW INDEX FROM tasks'
sudo mysql board_s2 -e 'SHOW INDEX FROM tasks'
```

`SHOW INDEX` печатает индексы таблицы, имя индекса стоит в колонке `Key_name`. Схема у всех шардов должна быть одинаковой. Сравни два вывода и найди, чего не хватает в шарде, где страницы ломаются. То же самое сделай для второй таблицы из ошибок.

## Выясни, кто изменил схему и что он сделает дальше

```bash
migratectl status
migratectl show
migratectl log
```

`status` показывает, какие шарды плановое изменение уже обработало и когда возьмётся за следующий. `show` печатает, что именно оно делает и почему его согласовали. `log` показывает время каждого шага: сравни его с временем первой ошибки из `access.log`. Теперь подумай, что случится с остальными пользователями, когда изменение дойдёт до их шардов. Если ещё не знаешь, как это предотвратить, выиграй время: пауза обратима, и бриф её разрешает.

## Найди, откуда приложение берёт имя, которого в базе больше нет

```bash
grep -rn '<имя из текста ошибки>' /etc 2>/dev/null
curl -s localhost:8080/admin/settings
```

Изменение само по себе законное: его проверяли и согласовали. Значит, вопрос в том, кто до сих пор обращается к удалённому по имени. `grep -rn` ищет текст во всех файлах каталога и печатает файл и номер строки. Прочитай найденный файл вместе с комментариями: там написано, зачем эта настройка появилась, как она попадает в запрос и как её выключают. Вторая команда показывает настройки, с которыми сервис работает прямо сейчас. Файл на диске и работающий сервис могут расходиться, пока сервису не сказали перечитать файл.

## Исправь, примени и проверь все страницы

Когда поймёшь, что именно в настройках сервиса больше не соответствует базе, исправь это и примени так, как написано в начале файла настроек. Потом убедись, что сервис действительно работает с новыми значениями, и повтори цикл из первого этапа:

```bash
curl -s localhost:8080/admin/settings
for u in 1042 2042 3042; do
  for p in "" /tasks /feed; do
    echo "$(curl -s -o /dev/null -w '%{http_code}' localhost:8080/users/$u$p) /users/$u$p"
  done
done
```

Смотри на обе страницы со списками, а не только на ту, с которой начал: у каждой свой запрос и своя ошибка.

## Доведи плановое изменение до конца и проверь ещё раз

```bash
migratectl status
migratectl help
```

Цель из брифа состоит из двух частей, и вторая из них это изменение, выполненное на всех трёх шардах. Продолжай его только после того, как страницы пострадавшего шарда снова открываются: тогда остальным шардам оно уже не повредит. `migratectl help` покажет, как снять паузу и как не ждать выдержку между шардами. После каждого шарда смотри `migratectl status` и повторяй цикл проверки страниц. Жми «Проверить», когда все три шарда обработаны и все девять строк цикла показывают `200`.
