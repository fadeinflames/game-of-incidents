# ALERT: BoardApi5xx > 15 %

Сервер `board-01`, сервис «Доска»: задачи и комментарии рабочих команд. Ты дежурный. Часть пользователей видит ошибку вместо своих страниц, у остальных всё открывается.

> 🎓 **Учебный кейс.** Если не знаешь, с чего начать, под брифом есть панель «Нужна помощь?»: она открывает этапы диагностики по одному и объясняет, зачем нужна каждая команда. Это бесплатно, как и подсказки 1 и 2. Та же задача без подсказок есть в каталоге под своим обычным названием.

## Что известно

- `board-api` слушает `127.0.0.1:8080` и только читает данные. У каждого пользователя три страницы: профиль `GET /users/<id>`, открытые задачи `GET /users/<id>/tasks` и лента его комментариев `GET /users/<id>/feed`.
- Данные лежат в MariaDB и разделены на три шарда: базы `board_s1`, `board_s2`, `board_s3`. Шард выбирается по id пользователя: 1001–1100 живут в `board_s1`, 2001–2100 в `board_s2`, 3001–3100 в `board_s3`. В большой системе шарды стояли бы на разных серверах, здесь это три базы одного MariaDB.
- Около пятой части запросов отвечает `500`. `GET /health` при этом отвечает `200`.
- Релизов `board-api` сегодня не было. Его настройки (`/etc/board-api/settings.conf`) давно никто не менял.
- Сегодня команда баз данных выполняет согласованное изменение схемы CHG-2291. Его ведёт сервис `migrator`: обрабатывает шарды по одному и после каждого выдерживает паузу. Что он делает сейчас, показывает `migratectl status`.

## Что не известно

- Кто именно получает ошибки и на каких страницах.
- В чём причина: в ответе с кодом `500` её нет.

## Цель

1. Все три страницы открываются с кодом `200` у пользователей всех трёх шардов.
2. Изменение CHG-2291 к концу работ выполнено на всех трёх шардах, и страницы после этого продолжают открываться.

## Ограничения

- CHG-2291 согласовано и нужно. Ставить его на паузу и продолжать можно. Отменять и откатывать нельзя: то, что оно уже сделало, руками не возвращаем.
- Схему баз руками не меняем, её меняет только `migrator`.
- Код в `/opt` только для чтения. Настройки сервисов в `/etc` менять можно.
- MariaDB без понятной причины не перезапускаем: перезапуск рвёт соединения всем пользователям сразу.

## Доступ

Пользователь `oncall`, `sudo` без пароля. Сервисы: `sudo service <имя> status|start|stop|restart` (или `systemctl`), имена: `mariadb`, `board-api`, `migrator`. Логи в `/var/log/<сервис>/`. База: `sudo mysql board_s1` (и `board_s2`, `board_s3`). Плановое изменение: `migratectl` без аргументов покажет состояние, `migratectl help` покажет остальные команды. Проверить страницу руками:

```bash
curl -i localhost:8080/users/1042/tasks
```

## Шпаргалка

| Команда | Что показывает |
|---|---|
| `curl -s -o /dev/null -w '%{http_code}\n' localhost:8080/users/<id>/tasks` | только код ответа страницы, удобно в цикле по пользователям и страницам |
| `tail -n 20 /var/log/board-api/access.log` | последние запросы: страница, код ответа, шард |
| `grep ' 500 ' /var/log/board-api/api.log \| tail -n 5` | ошибки сервиса с текстом, который вернула база, и с запросом |
| `sudo mysql board_s1 -e 'SHOW INDEX FROM tasks'` | индексы таблицы в выбранном шарде |
| `migratectl status`, `migratectl show`, `migratectl log` | что делает плановое изменение, зачем оно нужно и что уже сделано |
| `grep -rn '<текст>' /etc` | в каком файле и в какой строке встречается текст |
| `curl -s localhost:8080/admin/settings` | настройки, с которыми сервис работает прямо сейчас |
