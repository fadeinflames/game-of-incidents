## Что было сломано

Плановое обслуживание одного необычно большого репозитория занимало почти всю память сервера, и ядро убивало за это не обслуживание, а сервис хранилища.

- Студия перенесла в `studio/assets.git` архив исходников графики: 14 пушей по 4 файла. В репозитории стало 60 двоичных файлов по 5,5–7,5 МБ и 15 pack-файлов.
- `git-housekeeping` считает, что репозиторию пора на обслуживание, когда в нём больше 10 pack-файлов. Обслуживание это полная переупаковка `git repack -a -d -f`: дельты считаются заново.
- Когда git ищет дельты, каждый поток держит в памяти «окно» из последних объектов (`pack.window`, по умолчанию 10) вместе с их индексами. В байтах окно по умолчанию не ограничено (`pack.windowMemory = 0`), а потоков на сервере задано четыре (`pack.threads = 4` в `/etc/gitconfig`). На файлах по 6–7 МБ один объект окна занимает около 20 МБ, всё вместе около 800 МБ. Дельт между такими файлами нет, память тратится впустую.
- В `/etc/gitconfig` память при этом уже ограничивали: `core.packedGitLimit = 32m` не даёт отображать в память больше 32 МБ pack-файлов. На окно поиска дельт эта настройка не влияет.
- У сервера 640 МБ. Около 350 МБ постоянно занимает рабочий процесс `gitstored` со своим кэшем. Когда упаковка дорастает примерно до 260 МБ, память кончается.
- Ядро в такой момент убивает процесс с самой большой резидентной памятью. Это рабочий процесс `gitstored` (350 МБ против 260–270), а не виновник. Мастер `gitstored` запускает новый рабочий процесс только через `restart_delay = 90` секунд.
- Упаковка растёт дальше, упирается в лимит уже одна и тоже получает SIGKILL. Обслуживание не завершилось, pack-файлов по-прежнему 15, и через минуту cron запускает его снова.
- Итог: рабочий процесс `gitstored` живёт около 30 секунд из каждых двух минут. Пока его нет, `mergeq` не может создать ни одного merge-коммита и копит очередь. Когда он появляется, очередь разбирается за секунды. Запросы не теряются, они опаздывают на минуту-три, и вместе с ними опаздывают пайплайны.

## Как это диагностируется

1. `mergeq status` и `/var/log/mergeq/mergeq.log`: `storage http://127.0.0.1:8075 unavailable ([Errno 111] Connection refused): 37 merge requests wait, the oldest for 70 s`. Сам `mergeq` исправен, он ждёт хранилище.
2. `/var/log/gitstored/gitstored.log`: `master: worker 5411 was killed by signal 9 (SIGKILL) after 29 s; ... the next worker starts in 90 s`, и так каждые две минуты. SIGKILL процесс себе не посылает.
3. Кто убивает. `dmesg` в контейнере недоступен, но счётчик ядра виден: `grep oom_kill /sys/fs/cgroup/memory.events` прибавляет 1–2 каждую минуту. `cat /sys/fs/cgroup/memory.max` показывает 671088640: это и есть вся память сервера, а не те гигабайты, что показывает `free`.
4. Кто занимает память. `ps -eo pid,user,rss,etime,args --sort=-rss | head -5` несколько раз подряд в начале минуты: рядом с рабочим процессом `gitstored` (350 МБ) появляется `git pack-objects` пользователя `git` и за несколько секунд дорастает до 250 МБ и больше. После этого рабочего процесса `gitstored` в списке уже нет, а `pack-objects` растёт дальше, до 500–600 МБ. Его запустил `git repack -a -d -f` в `/var/lib/git/studio/assets.git`, а тот запущен из `git-housekeeping`.
5. `/var/log/git-housekeeping/housekeeping.log`: каждую минуту `studio/assets.git: due (15 packs > 10): git repack -a -d -f` и через 15–25 секунд `FAILED ... error: pack-objects died of signal 9`. Остальные репозитории обслуживаются за доли секунды. Два дня назад тот же репозиторий обслуживался за секунду: тогда в нём было четыре файла.
6. Что изменилось сегодня: `sudo -u git git -C /var/lib/git/studio/assets.git log --format='%cr %s' | head`, затем `count-objects -vH` и `ls-tree -r -l main | head`. Сегодняшний импорт: 56 файлов по несколько мегабайт.
7. Какие настройки действуют: `git-housekeeping --plan`, `cat /etc/gitconfig`, `sudo -u git git -C /var/lib/git/studio/assets.git config --show-origin --get-regexp '^(pack|core)\.'`. Число потоков задано, предела для окна нет.

## Эталонное решение

```bash
# 1. Предел памяти для упаковки, на весь сервер: 2 потока, окно не больше 16 МБ на поток.
sudo git config --system pack.windowMemory 16m
sudo git config --system pack.threads 2

# 2. Запуск, который начался до этого, работает со старыми настройками: остановить, cron запустит следующий.
sudo pkill -u git -f pack-objects

# 3. Хранилище: перезапуск возвращает рабочий процесс сразу, а не через 90 секунд. Очередь разбирается за секунды.
sudo service gitstored restart
mergeq status

# 4. Довести обслуживание большого репозитория до конца и убедиться, что хранилище его пережило.
sudo -u git git-housekeeping --force studio/assets.git
curl -s localhost:8075/health
```

С этими настройками обслуживание `studio/assets.git` занимает 75–90 МБ и идёт 10–15 секунд. Пока оно идёт, merge-коммиты создаются вовремя, хотя процессор занят так же плотно, как раньше: мешала память, а не процессор.

Что можно сделать иначе, проверка это принимает:

- Четыре потока и `pack.windowMemory 16m`: около 125 МБ. С `32m` выходит уже около 180 МБ, это больше отведённых 150. Предел считается на поток, и меньше двух-трёх объектов окно не становится, поэтому на крупных файлах итог заметно больше, чем «потоки × предел».
- Один поток и `pack.windowMemory 64m`: около 110 МБ.
- Не искать дельты там, где их не бывает: `core.bigFileThreshold 4m` в `config` репозитория или строка `*.tga -delta` в его `info/attributes`. Упаковка таких файлов почти не занимает памяти и идёт секунду. Для репозитория с двоичными файлами это самое точное лечение, а общий предел остаётся страховкой для следующего необычного репозитория.
- Настройки можно положить в `/etc/gitconfig`, в `config` репозитория или в `~git/.gitconfig`: обслуживание читает все три.
- `gitstored` можно не перезапускать: после того как его перестанут убивать, мастер сам поднимет рабочий процесс в пределах 90 секунд.

## Ловушки

- **Перезапустить `mergeq`.** Он исправен. Очередь лежит на диске и после перезапуска та же.
- **Перезапустить `gitstored` и на этом остановиться.** Рабочий процесс появляется сразу, очередь разбирается, алерт гаснет. В начале следующей минуты обслуживание убивает его снова.
- **Убить `git pack-objects`.** Память освобождается, но pack-файлов по-прежнему 15, и через минуту cron запускает обслуживание опять.
- **Отключить обслуживание, исключить `studio/assets.git` или поднять `max_packs`.** Симптом пропадает, а репозиторий навсегда остаётся с 15 pack-файлами, и каждый пуш добавляет новый. Условие это запрещает, проверка это видит: она сама запускает обслуживание этого репозитория.
- **`nice` и `ionice`.** Они меняют очередь к процессору и диску. Память они не ограничивают, а ядро при её нехватке на приоритеты не смотрит.
- **Только `ulimit -v` в строке cron.** Это предел без настройки: git упирается в него и падает с `fatal: failed to read object ...: Cannot allocate memory`, обслуживание репозитория не завершится никогда. К тому же `ulimit -v` ограничивает адресное пространство, а не занятую память. В него входят отображённые pack-файлы, библиотеки и стеки потоков, так что значение приходится подбирать: слишком большое не спасает `gitstored`, слишком маленькое роняет обслуживание даже с правильными настройками git. Предел полезен вместе с настройками, а не вместо них.
- **Только `pack.threads 1` или `2`.** Одно окно без предела это почти 200 МБ, два окна около 400. Число потоков уменьшает расход, но не ограничивает его: файлы вдвое крупнее дадут вдвое больше.
- **Уменьшить кэш `gitstored`.** Тогда самым большим процессом станет упаковка, и ядро будет убивать её. Merge-коммиты пойдут вовремя, а обслуживание так и не завершится. Настройки `gitstored` по условию не трогаем.
- **Уменьшить `restart_delay`.** Рабочий процесс будет возвращаться быстрее и так же быстро погибать.
- **Удалить импорт или очистить очередь.** Потеря данных вместо ремонта.

## Как было на самом деле

Сценарий сделан по сообщению GitHub об инциденте 20 сентября 2026 года. Всё, что известно, это несколько абзацев на странице статуса; подробного разбора компания не публиковала.

Что в них сказано:

- С 21:46 до 22:24 UTC сервис Pull Requests работал с деградацией: merge-коммиты и тестовые merge-коммиты создавались с опозданием, на пике около четырёх минут. Коммиты задерживались, а не терялись.
- Часть запусков Actions для событий pull request стартует только после создания merge-коммита, поэтому они тоже задержались.
- Причина: плановая задача обслуживания необычно большого репозитория заняла почти всю память одного сервера хранения Git, и этот сервер не мог обслуживать git-операции, которыми создаются merge-коммиты.
- В 22:18 UTC сервер вывели из работы, после этого накопившиеся merge-коммиты были созданы за шесть минут.
- Что компания изменила: ограничила память, которую может занять одна задача обслуживания репозитория, чтобы один репозиторий не мог исчерпать сервер, и улучшила мониторинг и оповещения о состоянии серверов хранения.

Чего в сообщении нет: какая именно задача обслуживания это была, чем репозиторий был необычен, как устроено ограничение и как именно нехватка памяти мешала серверу обслуживать запросы.

Чем стенд отличается от оригинала и что в нём придумано:

- Один сервер с 640 МБ вместо парка серверов хранения. В оригинале сервер вывели из работы, и запросы ушли на другие. В стенде других серверов нет, поэтому остаётся то, что компания сделала после инцидента: ограничить задачу.
- Репозиторий «необычно большой» по меркам стенда: 60 двоичных файлов, около 390 МБ в распакованном виде. Задача обслуживания это `git repack -a -d -f` из cron. Обёртка `git-housekeeping`, правило «пора, если больше 10 pack-файлов» и повтор через минуту придуманы для стенда.
- Расход памяти в стенде настоящий: так ведёт себя `git pack-objects` с настройками по умолчанию на крупных двоичных файлах. Процессы убивает настоящий OOM killer ядра в cgroup контейнера.
- Как нехватка памяти превращается в задержку merge-коммитов, это прочтение стенда, в сообщении этого нет. При подготовке сценария проверено измерением: в контейнере без подкачки мелкие git-операции от нехватки памяти почти не замедляются (5 мс превращаются в 10–90 мс, и это вклад процессора). Зато ядро убивает самый большой процесс. Поэтому сервис хранилища в стенде сделан таким, чтобы жертвой был он: `gitstored` с мастером, рабочим процессом, кэшем в 332 МиБ, который выделяется сразу, и паузой 90 секунд перед перезапуском это заглушка с подобранными размерами. На настоящем сервере с подкачкой и большим страничным кэшем картина, скорее всего, другая: сервер не падает, а вязнет.
- `mergeq`, очередь в каталоге и поток запросов `loadgen` тоже заглушки. Задержки в стенде до трёх минут, в оригинале до четырёх.
- В стенде ограничение делается настройками git, потому что создать отдельную cgroup для задачи в контейнере без привилегий нельзя. На обычном сервере жёсткий предел ставят именно так: `systemd-run -p MemoryMax=...` или `MemoryMax=` в юните задачи. Тогда при превышении умирает задача, а не сосед. Настройки git при этом всё равно нужны, иначе задача под пределом просто не завершится.

## Чему учит

- **OOM killer выбирает самого большого, а не виноватого.** Основной сервис обычно и есть самый большой процесс на сервере. Строка «worker was killed by signal 9» говорит о жертве. Виновника нужно искать отдельно, по росту памяти.
- **Фоновая задача без предела однажды встретит необычные данные.** Настройки по умолчанию годами работают на типичных репозиториях. Предел нужен не для них, а для одного нетипичного.
- **Предел и настройка это разные вещи.** Жёсткий лимит (cgroup, `ulimit`) защищает соседей, но задача под ним падает. Чтобы она ещё и завершалась, её нужно научить работать в этих рамках: `pack.windowMemory`, `pack.threads`, `core.bigFileThreshold`.
- **`nice` не про память.** Приоритет процессора и ввода-вывода не мешает задаче занять всю память.
- **В контейнере `free` показывает чужую память.** Свой лимит и счётчик убийств лежат в `/sys/fs/cgroup/memory.max` и `memory.events`.
- **«Убить и перезапустить» не решение, если есть расписание.** Задача, которая не завершилась, вернётся со следующим запуском. Сначала лечится причина, потом поднимается пострадавший.
- **Изменились данные, а не настройки.** «Настройки никто не трогал» не значит, что ничего не изменилось.
- **Следить нужно за здоровьем сервера, а не только за сервисом.** Счётчик `oom_kill` и свободная память сервера показали бы причину раньше, чем задержка merge-коммитов.
