# Как подступиться

«Сайт отвечает не тем, чем должен» разбирается одной лестницей: **воспроизвести → оценить масштаб → понять, кто именно ответил → посмотреть, что сервер загрузил на самом деле → сравнить с тем, что должно быть**. Спускайся сверху вниз и не перепрыгивай ступени.

## Воспроизведи жалобу и сравни со здоровым сайтом

```bash
curl -i -H 'Host: ufa.polka.example' http://127.0.0.1/
curl -i -H 'Host: msk.polka.example' http://127.0.0.1/
```

Заголовок `Host` говорит nginx, какой сайт ты спрашиваешь: DNS для этого не нужен. Смотри на первую строку ответа (код), на заголовок `Location` и на тело. У здорового сайта в теле есть строка `site=` с его именем: её пишет приложение. Запомни, чем отличаются два ответа и кто, судя по телу, ответил в первом случае.

## Оцени масштаб по логу

```bash
awk '{print $8, $4}' /var/log/nginx/access.log | sort | uniq -c | sort -k2,2n -k1,1nr | less
grep ' ufa.polka.example ' /var/log/nginx/access.log | awk '{print $2, $8, $10}' | uniq -f1 | head
```

В логе четвёртое поле хранит имя сайта, восьмое код ответа, поле `up=` говорит, какому приложению nginx передал запрос (`-` значит, что nginx ответил сам). Первая команда считает коды по сайтам: жалобы пришли на два сайта, а сколько их в списке с тем же кодом? Вторая показывает, когда ответы сайта изменились. Сравни это время с тем, что записано в `/etc/nginx/CHANGELOG`.

## Найди, какой блок nginx отвечает редиректом

```bash
grep -rn 'return 301' /etc/nginx/
```

`grep -rn` ищет текст во всех файлах каталога и печатает файл и номер строки. Открой найденный файл и прочитай комментарий в нём. Блок с `default_server` получает запросы, для имени которых у nginx нет своего блока `server`. Значит, вопрос теперь звучит так: почему nginx не знает имя `ufa.polka.example`?

## Посмотри, что nginx загрузил на самом деле

```bash
sudo nginx -T 2>/dev/null | grep -c 'server_name '
sudo nginx -T 2>/dev/null | grep 'ufa.polka.example'
grep -rl 'ufa.polka.example' /etc/nginx
```

`nginx -t` проверяет только то, что nginx прочитал. `nginx -T` печатает всё прочитанное целиком: главный файл и каждый подключённый. Первая команда считает имена в загруженной конфигурации (вместе с блоком по умолчанию, его имя `_`), вторая ищет в ней пострадавший сайт, третья ищет его же в файлах на диске. Если на диске сайт есть, а в выводе `nginx -T` его нет, посмотри, какими строками `nginx.conf` подключает файлы сайтов, и сравни с полным именем найденного файла.

## Сравни ожидаемый список с загруженным

```bash
awk '$1 == "server_name" {print $2}' /etc/nginx/nginx.conf.before-OPS-2107 | tr -d ';' | sort > /tmp/before
sudo nginx -T 2>/dev/null | awk '$1 == "server_name" {print $2}' | tr -d ';' | sort > /tmp/now
diff /tmp/before /tmp/now
find /etc/nginx/sites -type f | sort
```

До работ все сайты были в одном файле, его копия осталась. `diff` покажет, каких имён не хватает сейчас (строки с `<`) и какие появились (строки с `>`). Список пропавших и есть настоящий масштаб. `find` покажет все файлы сайтов: найди среди них файлы пропавших сайтов. Не всё, что не загружено, должно быть загружено: прежде чем что-то включать, прочитай первые строки файла.

## Исправь и проверь каждый сайт

Когда поймёшь, почему часть файлов nginx не читает, исправь это, затем проверь и примени конфигурацию:

```bash
sudo nginx -t && sudo service nginx reload
sleep 2
for h in $(grep -v '^_$' /tmp/before) sale.polka.example; do
  echo "$(curl -s -o /dev/null -w '%{http_code}' -H "Host: $h" http://127.0.0.1/) $h"
done > /tmp/codes
cut -d' ' -f1 /tmp/codes | sort | uniq -c
grep -v '^200 ' /tmp/codes
```

`reload` плавный: старые процессы nginx ещё мгновение отвечают по прежней конфигурации, поэтому перед проверкой стоит пауза. Цикл спрашивает каждый сайт из старого списка и новый `sale` и записывает код ответа. Предпоследняя команда считает, сколько каких кодов получилось, последняя печатает сайты, которые ответили не `200`: она должна промолчать. Такой цикл по списку ожидаемых сайтов и есть проверка, которой не хватило после работ. Только после этого жми «Проверить».
