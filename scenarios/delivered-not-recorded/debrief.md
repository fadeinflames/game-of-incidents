## Что было сломано

Релиз 2.0.0 конвейера менял формат, в котором `dispatcher` передаёт `recorder` запись о доставке. В релизе 1.8.3 запись потока `deliveries` состояла из отдельных полей (`delivery_id`, `hook_id`, `status` и так далее, формат 1). В 2.0.0 это один JSON-документ в поле `rec` (формат 2). Менять формат должны обе стороны: одна пишет, другая читает.

Релиз выкатывали по одному компоненту, и выкатка остановилась на полпути.

- `history-api` 2.0.0 выкатился. В нём нет функциональных изменений, к сбою он отношения не имеет.
- `recorder` 2.0.0 выкатился и с этого момента понимает только формат 2.
- `dispatcher` 2.0.0 не выкатился вообще. Манифест релиза поднимал ему лимит памяти с 96Mi до 256Mi, а LimitRange `tenant-limits` в namespace `hooks` разрешает контейнеру не больше 192Mi. Новый ReplicaSet не смог создать ни одного пода. Оба старых пода 1.8.3 остались работать и продолжили писать формат 1. Сломанного пода при этом нет: под, который запретили создать, в `kubectl get pods` не появляется.

Дальше сработала давняя и разумная на вид особенность `recorder`. С релиза 1.8.3 запись потока, которая не является записью о доставке, он подтверждает и пропускает, чтобы посторонняя запись не останавливала поток (HOOK-377 в CHANGELOG). Для `recorder` 2.0.0 запись без поля `rec` именно такая. Каждую запись старого формата он читал, подтверждал и не сохранял. Ошибки нет, перезапусков нет, группа читателей без отставания. Остаются счётчик `recorder_entries_skipped_total` и строка в логе на уровне debug.

Итог: уведомления доходят до клиентов, а в таблицу `deliveries` не попадает ни одна новая запись. `history-api` честно показывает то, что есть в таблице, и отвечает 404 на попытку повторной отправки.

## Как это диагностируется

1. Размер бедствия. Клиенты получили больше, чем знает журнал, и журнал остановился в момент выкатки:

   ```
   $ kubectl -n outside exec deploy/customers -- curl -s localhost:8080/stats
   {"deliveries_received": 153, "requests_total": 153, "deliveries_received_more_than_once": 0, "uptime_sec": 76}
   $ kubectl -n hooks exec deploy/history-api -- curl -s localhost:8080/stats
   {"deliveries_total": 42, "hooks": 6, "last_delivered_at": "2026-11-12T09:05:16.948+00:00"}
   ```

2. Путь записи по шагам. В потоке записи есть, и их столько же, сколько доставок. Группа `recorder` прочитала и подтвердила все:

   ```
   $ kubectl -n hooks exec deploy/redis -- redis-cli XLEN deliveries
   157
   $ kubectl -n hooks exec deploy/redis -- redis-cli XINFO GROUPS deliveries
   name recorder  consumers 1  pending 0  last-delivered-id 1794474372949-0  entries-read 157  lag 0
   ```

   (Вывод `XINFO` здесь сжат в одну строку.) В таблице их 42: `kubectl -n hooks exec deploy/postgres -- psql -U hooks -d hooks -c 'select count(*) from deliveries'`. Записи пропадают между потоком и таблицей, то есть в `recorder`. Заодно видно главное для восстановления: прочитанные и подтверждённые записи из потока никуда не делись.

3. `recorder` ни на что не жалуется. В логе одна строка каждые полминуты, и она правдива:

   ```
   09:05:49 INFO  30 s: 68 entries read, 68 acknowledged, consumer group lag 0
   ```

   Про «сохранено» в ней ничего нет. Это есть в метриках:

   ```
   $ kubectl -n hooks exec deploy/recorder -- curl -s localhost:9102/metrics | grep -v '^#'
   pipeline_build_info{component="recorder",release="2.0.0",record_format="2"} 1
   recorder_entries_read_total 115
   recorder_entries_acknowledged_total 115
   recorder_records_stored_total 0
   recorder_entries_skipped_total 115
   ```

   С `LOG_LEVEL=debug` (`kubectl -n hooks set env deploy/recorder LOG_LEVEL=debug`) причина написана прямо:

   ```
   DEBUG entry 1794474623448-0 is not a delivery record in handoff format 2 (fields: delivered_at,delivery_id,duration_ms,event,hook_id,payload_sha256,status): acknowledged, not stored
   ```

4. Кто в каком формате говорит. Первая строка лога каждого компонента и `pipeline_build_info` в метриках:

   ```
   recorder 2.0.0 starting: ... in handoff format 2 (JSON envelope in the stream field "rec")
   dispatcher 1.8.3 starting: ... in handoff format 1 (flat stream fields)
   ```

   То же видно по самой записи: `redis-cli XREVRANGE deliveries + - COUNT 1` показывает отдельные поля и ни одного `rec`. Разница между релизами лежит в одном файле: `diff /opt/pipeline/releases/1.8.3/recordfmt.py /opt/pipeline/releases/2.0.0/recordfmt.py`.

5. Почему версии разные. В Deployment записан релиз 2.0.0, а работают поды 1.8.3:

   ```
   $ kubectl -n hooks get pods -L app.kubernetes.io/version
   dispatcher-769bbbd587-pscbn    1/1     Running   0          101s   1.8.3
   dispatcher-769bbbd587-vmlvk    1/1     Running   0          101s   1.8.3
   history-api-664787df99-vjl7n   1/1     Running   0          79s    2.0.0
   recorder-7dd4df4b8c-ljcmc      1/1     Running   0          74s    2.0.0
   $ kubectl -n hooks get deploy dispatcher
   NAME         READY   UP-TO-DATE   AVAILABLE
   dispatcher   2/2     0            2
   ```

   `UP-TO-DATE 0` при `READY 2/2`: всё работает, и ничего не обновлено. `kubectl -n hooks describe deploy dispatcher` показывает `NewReplicaSet: dispatcher-d6cf875b9 (0/1 replicas created)` и условие `ReplicaFailure True FailedCreate` (в первые минуты оно то появляется, то пропадает между попытками ReplicaSet). События объясняют почему:

   ```
   $ kubectl -n hooks get events --sort-by=.lastTimestamp
   Warning   FailedCreate   replicaset/dispatcher-d6cf875b9   Error creating: pods "dispatcher-d6cf875b9-4txsx" is forbidden: maximum memory usage per Container is 192Mi, but limit is 256Mi
   ```

   `kubectl -n hooks rollout status deploy/dispatcher` не завершается: `Waiting for deployment "dispatcher" rollout to finish: 0 out of 2 new replicas have been updated...`. Через десять минут после начала выкатки Deployment получает условие `Progressing False ProgressDeadlineExceeded`, и та же команда сразу отвечает `error: deployment "dispatcher" exceeded its progress deadline`. Сам Kubernetes при этом ничего не откатывает: старые поды работают дальше.

## Эталонное решение

Сначала остановить потерю, потом вернуть потерянное. Клиентов при этом никто не трогает.

Самый короткий способ привести обе стороны к одному формату: вернуться в последнее состояние, где они друг друга понимали.

```bash
# 1. отменить выкатку dispatcher, которая так и не началась: иначе она пройдёт в тот день,
#    когда кто-нибудь поднимет потолок, и конвейер снова разойдётся
kubectl -n hooks rollout undo deploy/dispatcher --to-revision=1

# 2. вернуть recorder на 1.8.3: он читает то, что пишут диспетчеры
kubectl -n hooks rollout undo deploy/recorder --to-revision=1
kubectl -n hooks rollout status deploy/recorder
```

С этого момента новые доставки попадают в журнал. Номер ревизии лучше указывать явно: если до этого ты перезапускал Deployment или включал debug, `rollout undo` без номера вернёт предыдущую ревизию, а это тот же 2.0.0.

```bash
# 3. вернуть пропущенное: записи остались в потоке, подтверждение их не удаляет.
#    Группа читателей возвращается в начало потока, recorder читает его заново.
kubectl -n hooks exec deploy/redis -- redis-cli XGROUP SETID deliveries recorder 0
```

Перезапускать `recorder` не нужно: следующий же `XREADGROUP` отдаст ему записи с начала. Повторов в таблице не будет, потому что `delivery_id` это первичный ключ, а `recorder` пишет `INSERT ... ON CONFLICT (delivery_id) DO NOTHING`. По счётчикам видно, что произошло:

```
recorder_records_stored_total 761
recorder_records_already_stored_total 79
recorder_entries_skipped_total 0
```

После этого `XLEN deliveries` и `select count(*) from deliveries` совпадают, а у возвращённых записей `recorded_at` заметно позже `delivered_at`: по этому признаку их потом легко найти. Релиз 2.0.0 после этого нужно выкатывать заново и иначе, об этом ниже.

**Другое направление: довести выкатку до конца.** Тоже засчитывается. `dispatcher` 2.0.0 не выкатился из-за лимита памяти, потолок менять нельзя, значит, лимит надо уложить в него:

```bash
kubectl -n hooks set resources deploy/dispatcher --limits=memory=192Mi
kubectl -n hooks rollout status deploy/dispatcher
```

Новые записи пойдут в формате 2, и `recorder` 2.0.0 их сохранит. Но записи за время сбоя лежат в потоке в формате 1, и `recorder` 2.0.0 пропустит их снова. Поэтому возврат делается в два прохода: на время вернуть `recorder` 1.8.3 и перечитать поток с начала (он сохранит записи формата 1 и пропустит формат 2), затем вернуть `recorder` 2.0.0 и перечитать поток ещё раз (он сохранит формат 2, пропущенный на первом проходе). Оба прохода безопасны по той же причине: таблица не принимает дубликаты.

```bash
kubectl -n hooks rollout undo deploy/recorder --to-revision=1 && kubectl -n hooks rollout status deploy/recorder
kubectl -n hooks exec deploy/redis -- redis-cli XGROUP SETID deliveries recorder 0
# дождаться, пока recorder_records_stored_total перестанет расти
kubectl -n hooks rollout undo deploy/recorder --to-revision=2 && kubectl -n hooks rollout status deploy/recorder
kubectl -n hooks exec deploy/redis -- redis-cli XGROUP SETID deliveries recorder 0
```

Номер ревизии с релизом 2.0.0 смотри в `kubectl -n hooks rollout history deploy/recorder`: после первого отката он может быть другим.

Грейдер смотрит на результат: три его собственные доставки появляются в журнале, в журнале есть запись о каждой доставке, которую получили клиенты, нет записей без доставки, нет повторных доставок, и ни у одного Deployment конвейера не осталось незавершённой выкатки.

## Ловушки

- **Перезапустить `recorder` или `dispatcher`.** Ничего не меняет: после перезапуска каждый говорит на своём формате. У `dispatcher` есть и вторая сторона: `kubectl rollout restart` создаёт ещё одну ревизию с тем же лимитом 256Mi, она так же упирается в LimitRange, и ни один под на самом деле не перезапускается.
- **Откатить `history-api`.** Его обновляли сегодня, и жалуются именно на журнал, поэтому он первый подозреваемый. Но он только читает таблицу, а записей нет в самой таблице.
- **Откатить только `dispatcher`.** Он и так работает на 1.8.3. Откат убирает застрявшую выкатку, это полезно, но `recorder` по-прежнему ждёт формат 2.
- **Отправить клиентам всё ещё раз.** На стенде это выглядит как `XGROUP SETID events dispatcher 0`: группа `dispatcher` возвращается в начало потока событий, и клиенты получают каждое уведомление о платеже повторно. Вернуть это нельзя. Записи при этом в журнале не появляются: идентификатор доставки выводится из идентификатора события, и повтор приходит с тем же `delivery_id`. Легко перепутать потоки: возвращать нужно группу `recorder` в потоке `deliveries`, а не группу `dispatcher` в потоке `events`.
- **Очистить поток `deliveries` или перезапустить Redis.** Пропущенные записи лежат только там. `XTRIM`, `DEL` или перезапуск Redis (он хранит потоки в памяти) делают потерю окончательной.
- **Удалить группу читателей.** `XGROUP DESTROY deliveries recorder` сам по себе ничего не чинит: `recorder` создаёт группу заново с начала потока и пропускает те же записи ещё раз. Когда обе стороны уже согласованы, это грубая замена `XGROUP SETID ... 0`, но отставание и список неподтверждённых записей группы при этом теряются.
- **Дописать строки в таблицу руками, чтобы сошлись числа.** Грейдер сверяет не количество, а идентификатор каждой доставки и хэш её тела с тем, что получили клиенты. Выдуманные строки он находит и считает отдельно.
- **Поднять потолок LimitRange или удалить его.** Он принадлежит платформенной команде и защищает ноду от соседей; грейдер проверяет, что он на месте. Чтобы довести выкатку до конца, достаточно уложить лимит `dispatcher` в разрешённые 192Mi.
- **Остановить `emitter`, «чтобы не росла потеря».** Вместе с потерей записей останавливаются сами уведомления о платежах, а это уже сбой для всех клиентов.

## Как было на самом деле

Сценарий сделан по мотивам инцидента GitHub 14 июля 2026 года. О нём известно только то, что компания написала на странице статуса; всё остальное на стенде придумано.

**Что сообщила компания.**

- С 15:17 до 15:37 UTC выкатка во внутреннем конвейере доставки webhook привела к тому, что часть записей о доставках не была записана в хранилище доставок, хотя сами доставки были обработаны и успешно отправлены.
- Причиной названа несогласованная выкатка: изменение способа, которым записи о доставках передаются между компонентами конвейера, было развёрнуто раньше, чем обновили вышестоящие компоненты, которые эти записи создают. Пока выкатка шла, такие записи молча пропускались вместо сохранения, и автоматического повтора не было.
- Пропущено около 2,4 млн записей: примерно 4 % за двадцать минут сбоя и 0,04 % обычного суточного объёма. 95 % этих доставок дошли до серверов клиентов, отсутствует только запись. Из оставшихся примерно 5 % лишь около 1,4 % (5 463) относятся к webhook, по которым за последние 28 дней делали повторные доставки.
- Пропавшие доставки не видны в интерфейсе и API и недоступны для повторной отправки.
- Сбой закончился сам, когда выкатка завершилась.
- После инцидента компания улучшает автоматическое обнаружение небезопасных изменений схемы и ужесточает согласование выкаток, которые затрагивают несколько компонентов конвейера.

**Чем стенд отличается.**

- В настоящем инциденте выкатка дошла до конца сама, и сбой длился двадцать минут. На стенде она застряла на полпути, и записи теряются, пока кто-нибудь не вмешается. Причина остановки (лимит памяти в манифесте выше потолка LimitRange) придумана: компания о таком не сообщала.
- В настоящем инциденте пропущенные записи не вернули: компания прямо пишет, что эти доставки не появятся в журнале и не будут доступны для повторной отправки. На стенде их можно вернуть, потому что запись, прочитанная из потока Redis, в нём остаётся. Это решение автора сценария, сделанное ради учебной части. Как устроена передача записей у компании и было ли там что перечитывать, неизвестно.
- Redis Streams, PostgreSQL, имена компонентов, два формата записи, правило «подтвердить и пропустить то, что не похоже на запись о доставке», счётчик и строка debug придуманы. Компания сообщила только, что записи пропускались молча.
- На стенде все доставки доходят до клиентов. В настоящем инциденте около 5 % пропущенных записей относились к доставкам, которые до клиентов не дошли.
- Под `customers`, у которого можно спросить, что получили клиенты, существует только на стенде.

## Чему учит

- **«Нет ошибок» не значит «работа сделана».** Компонент, который молча пропускает непонятное, выглядит здоровым: он читает, подтверждает, не отстаёт. Сверять надо вход с выходом: сколько записей пришло и сколько сохранено. Алерт на долю пропущенных записей поймал бы этот сбой за минуту.
- **Изменение формата между двумя компонентами это три выкатки, а не одна.** Сначала читатель учится понимать оба формата, потом писатель переходит на новый, потом у читателя убирают старый. При такой схеме нет ни порядка выкатки, который надо соблюсти, ни момента, когда остановившаяся выкатка что-то ломает. В релизе 2.0.0 этого не было, поэтому правильного порядка для него не существует: при любом порядке есть окно, в котором записи пропускаются.
- **Выкатка может остановиться, не сломав ни одного пода.** `READY 2/2` и `UP-TO-DATE 0` означают, что работает старая версия. Причину показывают условия Deployment и события ReplicaSet, а не список подов.
- **Подтвердить не значит удалить.** В Redis Streams `XACK` убирает запись из списка неподтверждённых у группы, а в потоке она остаётся до обрезки. Пока поток не обрезан, группу можно вернуть назад и перечитать его.
- **Идемпотентная запись делает повторную обработку безопасной.** Первичный ключ по `delivery_id` и `ON CONFLICT DO NOTHING` позволяют перечитать поток целиком, не разбираясь, что уже сохранено.
- **Повторная обработка и повторная отправка это разные вещи.** Перечитать свои записи можно сколько угодно раз. Отправить клиенту то же уведомление о платеже второй раз нельзя ни разу.
- **При сбое данных первым делом сохраняй то, из чего их можно восстановить.** Перезапуск Redis или очистка потока здесь выглядят безобидной гигиеной и уничтожают единственную копию.
