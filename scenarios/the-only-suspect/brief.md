# ALERT: StorageApiErrors > 80 %

Сервер `meta-01`, слой метаданных объектного хранилища. Клиенты не могут ни прочитать, ни записать объект: запросы висят несколько секунд и заканчиваются ошибкой.

## Что известно

- Запрос идёт так: клиент → `storage-api` (127.0.0.1:8080) → PostgreSQL 15, база `metadata`, таблица `objects`. В ней по пути объекта записано, на каких серверах он лежит.
- `GET /objects/<путь>` и `PUT /objects/<путь>` отвечают 504 или 503. `GET /healthz` отвечает 200: простые запросы база выполняет.
- Сервис `changefeed` передаёт изменения таблицы `objects` в биллинг: триггер на таблице складывает их в `object_changes`, сервис раз в секунду дописывает их в `/var/lib/changefeed/feed.jsonl`. Лента тоже остановилась.
- Релизов сегодня не было, настройки базы и сервисов не менялись несколько месяцев.
- Второй дежурный видел в `pg_stat_activity` один работающий процесс и предлагает снять его или перезапустить базу.

## Что не известно

- Почему запросы к одной таблице ждут, если база жива.
- Кто кого на самом деле держит.
- Почему это случилось именно сейчас, без единого изменения.

## Цель

Запись и чтение объектов через API работают, лента изменений доставляет события, и сбой не вернётся сам: ни через минуту, ни после перезапуска или переподключения сервисов, ни во время следующей долгой операции на таблице.

## Ограничения

- Перезапускать сервисы и базу можно, но перезапуск сам по себе решением не считается.
- Автовакуум и защита от переполнения счётчика транзакций должны остаться включёнными.
- `changefeed` должен работать: по его ленте биллинг считает использование.
- Данные в `objects` терять нельзя.
- Код в `/opt` только для чтения. Настройки сервисов лежат в `/etc`.

## Доступ

Пользователь `oncall`, `sudo` без пароля. База: `sudo -u postgres psql -d metadata`. Сервисы управляются через `service <имя> status|start|stop|restart` (или `systemctl`), логи лежат в `/var/log/<сервис>/`, лог базы в `/var/log/postgresql/`.
