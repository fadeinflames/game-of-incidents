## Что было сломано

Основной узел балансов после перезапуска поднялся с чужим файлом конфигурации: пустым и доступным только для чтения. Биллинг принял пустоту за нулевые балансы.

- Шесть дней назад система управления конфигурацией `cfgsync` перезаписала `/etc/redis/balances.conf`: в её инвентаре узел `balances` на `billing-01` значился репликой, и файл был отрисован по шаблону реплики. Сервис она не перезапускала, поэтому ничего не произошло: работающий Redis свой файл не перечитывает.
- Сегодня ночью предыдущая смена перезапустила `redis-balances`. При остановке Redis сохранил все 40 балансов в `dump.rdb`. При запуске он прочитал новый файл, и в нём сработали две строки.
- `appendonly yes`. С включённым AOF Redis при старте загружает данные только из append-only файла, а `dump.rdb` не читает вовсе. AOF у основного узла никогда не было, поэтому он создал пустой и стартовал с нулём ключей. Снимок с балансами при этом остался лежать рядом нетронутым.
- `replicaof 127.0.0.1 6379`. В шаблоне реплики это адрес основного узла, то есть самого этого узла. Redis стал репликой самого себя: синхронизация никогда не завершится (`-NOMASTERLINK Can't SYNC while not connected with my master`), а запись запрещена, как у любой реплики.
- `billing-worker` читает баланс командой `GET` и отсутствие ключа считает нулём. Для счёта с автопополнением ноль ниже порога, поэтому воркер списывает деньги с карты, пытается зачислить их на баланс и получает `READONLY`. Баланс не изменился, и следующее сообщение или звонок этого клиента запускает то же самое. Каждое событие стоит цент или три, а списывается за него 20 или 50 долларов.
- Счета без автопополнения пострадали иначе: при «нулевом» балансе воркер отказывался тарифицировать их события.
- Реплики на 6380 и 6381 всё это время держали старые балансы: к основному узлу они подключиться не могли и отдавали то, что успели получить до перезапуска.

## Как это диагностируется

1. `/var/log/cardproc/cardproc.log` растёт на строку каждые пару секунд, одни и те же счета повторяются. Это деньги клиентов, поэтому первым делом `sudo service billing-worker stop`, а разбираться уже после.
2. `/var/log/billing-worker/worker.log`: `balance update failed ... READONLY You can't write against a read only replica`, затем `auto-recharge account=... balance=-2 threshold=1000`, затем `charge ch_... not credited`. Воркер видит баланс около нуля и не может ничего записать.
3. `redis-cli -p 6379 dbsize` отвечает 0, `redis-cli -p 6380 dbsize` отвечает 40. Основной узел пуст, реплики нет.
4. `redis-cli -p 6379 info replication`: `role:slave`, `master_host:127.0.0.1`, `master_port:6379`, `master_link_status:down`. Основной узел считает себя репликой самого себя.
5. `/var/log/redis-balances/redis.log`, два последних запуска. Первый: `Done loading RDB, keys loaded: 40`. Второй: `Creating AOF base file appendonly.aof.1.base.rdb on server start`, про RDB ни слова, дальше бесконечное `Connecting to MASTER 127.0.0.1:6379`.
6. `redis-cli -p 6379 info server | grep config_file` показывает `/etc/redis/balances.conf`. В заголовке файла написано `Template: redis/replica.conf.tmpl ... Role: replica`, дата изменения шесть дней назад. `/var/log/cfgsync/cfgsync.log` объясняет, откуда он взялся, и называет прежнюю версию: `/var/backups/cfgsync/redis/balances.conf.<дата>`. `diff` между ними показывает ровно эти строки.
7. `sudo ls -la /var/lib/redis/balances`: `dump.rdb` с временем перезапуска и рядом свежий каталог `appendonlydir` с пустой базой. Данные на диске ещё есть, но любое сохранение их затрёт.

## Эталонное решение

Порядок важнее всего: остановить списания, сохранить то, что уцелело, починить узел, вернуть деньги и балансы, запустить биллинг.

```bash
# 1. Новых списаний больше нет
sudo service billing-worker stop

# 2. Снимок с балансами на момент перезапуска ещё цел: копия в сторону до любых перезапусков
sudo cp -p /var/lib/redis/balances/dump.rdb /root/balances-before-fix.rdb

# 3. Основному узлу возвращается его конфигурация
diff /etc/redis/balances.conf /var/backups/cfgsync/redis/balances.conf.*
sudo cp /var/backups/cfgsync/redis/balances.conf.* /etc/redis/balances.conf
sudo service redis-balances restart
redis-cli -p 6379 info replication | head -3      # role:master, connected_slaves:2
sudo rm -rf /var/lib/redis/balances/appendonlydir # пустой AOF от неудачного запуска больше не нужен

# 4. Возвраты: все списания, которые воркер не смог зачислить (настоящие балансы были выше порога)
grep 'not credited' /var/log/billing-worker/worker.log | grep -o 'ch_[0-9]*' | sort -u | sudo xargs billing-refund

# 5. Балансы из журнала: баланс счёта равен сумме его проводок
sqlite3 /var/lib/billing/billing.db \
  "SELECT 'SET balance:' || account_id || ' ' || SUM(amount_cents) FROM ledger GROUP BY account_id" | redis-cli -p 6379
redis-cli -p 6380 dbsize                          # 40: реплики подключились сами и получили копию

# 6. Биллинг снова работает, новых списаний нет
sudo service billing-worker start
tail /var/log/billing-worker/worker.log /var/log/cardproc/cardproc.log
```

Что здесь можно сделать иначе:

- Узел можно починить и без перезапуска: `redis-cli -p 6379 replicaof no one`, `config set appendonly no`. Но тогда обязательно исправить и файл (руками или командой `config rewrite`), иначе следующий перезапуск повторит аварию. Грейдер это проверяет: поднимает копию данных с тем файлом, который указан сервису, и смотрит, остались ли балансы и роль.
- Список ошибочных списаний можно получить и из базы процессинга: это все списания после перезапуска основного узла (время есть в `redis.log`). Ни у одного счёта настоящий баланс в это время не был ниже порога, это видно по сумме проводок. Законных пополнений за последние сутки было семь, и все они раньше.
- Возвраты нужно оформить до расчёта балансов: проводка `refund` входит в сумму. Если посчитать балансы раньше, у клиентов останутся лишние деньги, которые им уже возвращают на карту.
- Перезапуск на шаге 3 затирает `dump.rdb` пустым снимком. Здесь это допустимо, потому что копия сохранена, а балансы всё равно берутся из журнала.

Чего в стенде нет, но в жизни нужно: исправить роль узла в инвентаре `cfgsync`, иначе следующий прогон снова положит на диск конфигурацию реплики.

## Ловушки

- **Чинить Redis при работающем воркере.** Пока идёт диагностика, каждую пару секунд уходит новое списание; за 11–12 минут их набирается больше 400. А в момент, когда узел уже принимает запись, но ещё пуст, воркер спишет с каждого активного счёта ещё раз и запишет в Redis балансы, посчитанные от нуля. Эти списания в логе помечены `credited`, но они тоже ошибочные и тоже подлежат возврату.
- **Перезапустить основной узел ещё раз.** В прошлый раз «помогло», задержки пропали. Второй перезапуск с тем же файлом ничего не меняет, зато при остановке Redis сохраняет текущее состояние, то есть пустоту, поверх `dump.rdb`. Последняя копия балансов на диске пропадает.
- **`SAVE` или `BGSAVE` «на всякий случай».** То же самое без перезапуска: пустой набор ключей записывается поверх хорошего снимка.
- **Восстановить балансы из снимка или с реплики и на этом закончить.** В `dump.rdb`, на репликах и в `/var/backups/redis` лежат балансы на момент перезапуска или раньше. Расходы за время инцидента в них не учтены, а в журнале они есть. Балансы разойдутся с журналом у тех счетов с автопополнением, которые успели что-то потратить.
- **Сделать основной узел мастером, не подумав о репликах.** Как только пустой узел становится мастером, реплики делают полную синхронизацию и теряют старые балансы. Если реплики были последней копией данных, её больше нет.
- **Вернуть все списания за сутки.** Семь из них законные пополнения: баланс был ниже порога, деньги зачислены клиентам. Возврат такого списания уменьшает баланс клиента в журнале и уводит его в минус.
- **Выставить балансы на глаз.** Например, всем по сумме автопополнения. Журнал проводок существует именно для того, чтобы так не делать.
- **Отключить автопополнение клиентам или поправить проводки.** Списания прекратятся, но это настройки и деньги клиентов, а причина остаётся на месте.

## Как было на самом деле

Сценарий сделан по мотивам сбоя биллинга Twilio 18 июля 2013 года.

- Текущие балансы клиентов Twilio держала в кластере Redis: один мастер и несколько реплик в разных дата-центрах. Ночью связь между репликами и мастером пропала. Когда она вернулась, все реплики одновременно запросили полную синхронизацию, мастер оказался перегружен и стал отвечать с задержками.
- Дежурные инженеры увидели нагрузку и перезапустили мастер. При перезапуске Redis прочитал неправильный файл конфигурации. Файл предписывал восстанавливаться из AOF, которого не существовало, а не из бинарного снимка, и мастер поднялся без данных. Тот же файл делал его репликой самого себя, поэтому он работал только на чтение.
- Биллинг увидел нулевые балансы. У клиентов с автопополнением каждое тарифицируемое событие запускало списание с карты, обновить баланс не удавалось, и списание повторялось. Часть аккаунтов была заблокирована: повторные списания привели к блокировке карт, а следующая неудачная попытка пополнения отключала аккаунт.
- Мониторинг заметил аномалию через 46 минут после перезапуска, ещё через 42 минуты биллинг выключили. Балансы восстановили по записям двойного учёта в реляционной базе.
- Через несколько часов биллинг включили, и аномалия повторилась, задев ещё 0,3 % клиентов. Биллинг снова выключили. Всего пострадало 1,4 % клиентов.
- Возвраты заняли около суток. Пострадавшим клиентам дополнительно начислили 10 % от их расходов за последние 30 дней.

Чем стенд отличается от оригинала:

- Мастер и реплики стоят на одном сервере на разных портах, счетов 40, списания идут каждые две секунды.
- Версия Redis современная (7.0 из Debian 12). AOF в ней хранится каталогом с манифестом, но поведение прежнее: при `appendonly yes` снимок `dump.rdb` не загружается, даже если AOF пуст. Реплика самого себя тоже ведёт себя как в 2013 году: только чтение и бесконечные попытки синхронизации.
- Откуда у Twilio взялся неправильный файл, в разборе не сказано. История с `cfgsync` и ролью в инвентаре придумана для стенда.
- Блокировки аккаунтов нет: счетам без автопополнения воркер просто отказывает в тарификации.
- Поток событий генерирует сам воркер, поэтому при его остановке события не копятся.

Что компания изменила после сбоя: заменила кластер Redis, нашла и исправила конфигурацию мастера, запретила перезапускать мастер (восстановление теперь идёт через повышение реплики), добавила в биллинг защиту (если баланса нет или его нельзя записать, аккаунты не блокируются и карты не списываются) и пообещала сверять балансы с записями двойного учёта в реальном времени.

## Чему учит

- **Сначала останови ущерб.** Когда система каждую секунду делает что-то необратимое с чужими деньгами, первая команда останавливает её, а не ищет причину.
- **Перезапуск читает то, что лежит на диске.** Работающий процесс может месяцами жить с настройками, которых в файле уже нет. Перезапуск «чтобы помогло» применяет все накопившиеся изменения разом. Перед перезапуском хранилища стоит сравнить файл с тем, что отвечает `CONFIG GET`.
- **Перед любым действием с хранилищем сохрани то, что цело.** Копия `dump.rdb` занимает секунду. `SAVE`, `SHUTDOWN` и перезапуск на пустом узле уничтожают её без единого предупреждения.
- **«Ключа нет» и «баланс ноль» не одно и то же.** Код, который работает с деньгами, должен различать отсутствие данных и нулевое значение и при сомнении ничего не списывать.
- **Нужен независимый источник истины.** Журнал проводок в другой базе позволил восстановить всё до цента. Кэш, даже с репликами и снимками, такой гарантии не даёт: все копии здесь зависели от одного узла.
- **Управление конфигурацией без перезапуска копит мины.** Изменённый, но не применённый файл хуже, чем ошибка при выкатке: он сработает в самый неудобный момент, во время другого инцидента.
