# Разбор: Недостающие права

## Что было сломано

«Харднинг» сделал два изменения: ключ `/etc/backup/backup.key` стал `root:root 0600` (раньше `root:backup 0640`), а пользователя `backup` убрали из группы `app`, при этом `/srv/app/data` имеет права `0750 app:app`. Скрипт под `backup` не мог ни прочитать ключ, ни войти в каталог данных, и падал с `Permission denied`. Cron честно запускал его каждую ночь.

## Как это диагностируется

1. `tail /var/log/backup.log` — в логе только одна ошибка: `can't read key /etc/backup/backup.key (Permission denied)`. Скрипт выходит на проверке ключа и до `tar` не доходит, поэтому вторую проблему лог не показывает.
2. `sudo -u backup /usr/local/bin/backup.sh` — воспроизводит проблему за секунду, не дожидаясь ночи. После починки ключа повторный запуск покажет вторую ошибку: `tar: /srv/app/data: Cannot open: Permission denied`.
3. `id backup`, `ls -ld /srv/app/data`, `ls -l /etc/backup/backup.key` — кто, в каких группах, и что кому разрешено.

## Эталонное решение

(минимальные права, а не 777)

```bash
sudo usermod -aG app backup                 # доступ к данным через группу
sudo chgrp backup /etc/backup/backup.key    # ключ читает только группа backup
sudo chmod 640 /etc/backup/backup.key
sudo -u backup /usr/local/bin/backup.sh     # проверить сразу, а не ждать ночи
ls -l /var/backups/app/
```

Любое решение, при котором скрипт под `backup` успешно создаёт расшифровываемый архив, ключ не читаем «всем», каталог данных не открыт «всем», а владельцы остались прежними (ключ у `root`, каталог данных у `app`, и приложение может в него писать), засчитывается.

## Ловушки

- `chmod 777` на каталог или `chmod o+r` на ключ: бэкап заработает, но харднинг отменён целиком. Грейдер отклонит.
- `chown -R backup /srv/app/data`: бэкап заработает, а приложение потеряет запись в собственные данные. Следующий инцидент будет уже не про бэкап.
- `chown backup /etc/backup/backup.key`: тот, кто делает бэкап, теперь может подменить ключ. Читать ключ ему нужно, владеть им — нет.
- Проверять починку через `sudo /usr/local/bin/backup.sh`: от root работает всё, и это ничего не говорит о ночном job под `backup`.

## Чему учит

- Права на файлы проверяются на каждом шаге пайплайна, и «job запустился» ≠ «результат есть». Алертить надо на артефакт.
- Минимальные права решаются группами, а не открытием всего для всех.
- Воспроизводи ночной job руками под тем же пользователем: `sudo -u <user> …`.
