# 🟠 Загрузка файлов сломана — «аватар не сохраняется»

**Время:** понедельник, 10:05. Ты дежурный по платформе.

## Что известно

- `media-api` (namespace `media`, 2 реплики) хранит аватары и вложения в S3‑совместимом хранилище (`Deployment s3` в namespace `storage`, бакет `media`). Ключ доступа лежит в `Secret media/media-s3`.
- Ключи в приложения не кладут руками: security держит актуальный ключ в своём namespace (`security/s3-credentials`, «vault»), а `CronJob media/secret-sync` раз в 15 минут копирует его в `media-s3` и перезапускает `media-api`. Это внутрикластерный аналог ExternalSecret.
- Ночью security ротировала ключ хранилища. С утра пользователи получают 500 на загрузке; старые аватары и вложения при этом открываются.
- Приложение в остальном работает, поды `Ready`.

## Что не известно

- Почему приложение не подхватило новый ключ, если синхронизация автоматическая.
- Что ещё поменяла security кроме самого ключа.

## Цель

Загрузка через `media-api` работает, старые файлы читаются, `media-api` в 2 из 2 Ready, `media-s3` совпадает с ключом в vault, а `secret-sync` снова может читать vault, чтобы следующая ротация не повторила инцидент. CronJob не удалять.

## Ограничения

- Ключ из `storage/storage-root` напрямую в `media-s3` не копировать: источник правды для приложений — vault, иначе синхронизация затрёт его при следующем запуске.
- Отключать `secret-sync` «чтобы не мешал» нельзя.

## Доступ

Shell на bastion‑хосте с `kubectl` под пользователем `oncall`, кластер уже в kubeconfig; права cluster-admin. Проверить загрузку: `kubectl -n media exec deploy/media-api -- wget -qO- --post-data=test http://127.0.0.1:8080/upload/test.txt`.
