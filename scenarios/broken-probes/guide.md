# Как подступиться

Любой «под не поднимается» разбирается одной и той же лестницей: **состояние раскатки → список подов → события конкретного пода → манифест**. Спускайся по ней сверху вниз и не перепрыгивай ступени.

## Спроси у Deployment, на чём он застрял

```bash
kubectl rollout status deploy/web --timeout=5s
```

Команда ждёт завершения раскатки; `--timeout=5s` нужен, чтобы она не висела вечно. В ответе смотри на фразу *«N of 3 updated replicas are available»*: она говорит, сколько подов новой версии кластер считает рабочими.

## Посмотри на поды глазами кластера

```bash
kubectl get pods -l app=web -o wide
```

`-l app=web` отбирает только поды приложения, `-o wide` добавляет ноду и IP. Важные колонки: `READY` (`0/1` значит контейнер запущен, но readiness‑проба его не пропускает), `STATUS` и `RESTARTS` (растущее число перезапусков у свежего пода — почти всегда liveness‑проба). Старые и новые поды различаются возрастом в `AGE`.

## Спроси у проблемного пода, что с ним не так

```bash
kubectl describe pod <имя нового пода>
```

Главная команда при любом «не Ready». Листай до блока `Events` в самом низу: там кластер пишет, какая проба упала и с каким кодом. Код ответа HTTP скажет больше, чем любая гипотеза: `404` и `500` — разные истории.

## Сверь, что проверяет проба, с тем, что умеет приложение

```bash
kubectl get deploy web -o yaml | grep -n -A4 -i 'probe'
kubectl get deploy web -o yaml | grep -n -B1 -A1 HEALTH_PATH
```

Первая команда показывает пути и порты `readinessProbe`/`livenessProbe`, вторая — переменную окружения, которой релиз задаёт свой эндпоинт здоровья. Проба и приложение должны договориться об одном и том же пути.

## Исправь и дождись раскатки

Когда поймёшь, что не сходится, поправь Deployment (`kubectl edit deploy web` или `kubectl patch`) и снова выполни первый шаг, а потом:

```bash
kubectl get endpoints web
```

Три адреса в endpoints — значит сервис снова видит все реплики. Только после этого жми «Проверить».
